# 12 · 版本新特性（8 / 11 / 17 / 21 / 25）

> 目标：每个 LTS 能讲 4～6 条「能落地」的特性；21 重点虚拟线程；25 诚实跟官方 Release。

---

## 面试题

### Q1. Java 8 新特性（详细）

Java 8 是至今影响最大的一次语言/库升级，建议按块答：

**1）语言**

- Lambda 表达式、方法引用  
- 函数式接口（`@FunctionalInterface`）：`Function`/`Predicate`/`Consumer`/`Supplier`  

**2）Stream API**

- 声明式处理集合：`filter/map/reduce/collect`  
- 可并行（注意线程安全与场景）  

**3）Optional**

- 显式处理缺失值，减少 NPE；别滥用在字段与序列化  

**4）接口演化**

- `default` / `static` 方法，接口可加实现而不破坏全部实现类（仍有冲突规则）  

**5）日期时间**

- `java.time`：`LocalDate`/`LocalDateTime`/`ZonedDateTime`/`Instant`，不可变、清晰时区  

**6）并发**

- `CompletableFuture` 组合异步  

**7）JVM/其它**

- 永久代 → 元空间；HashMap 树化等  

**口述收尾：** 我们项目里用得最多的是 Lambda+Stream、Optional、新时间 API。

### Q2. Java 11（LTS）

1. **HTTP Client** 正式版：`java.net.http`，支持 HTTP/2、WebSocket  
2. 单文件启动：`java Hello.java`  
3. String 增强：`isBlank`、`strip`、`lines`、`repeat`  
4. `var` 可用于 Lambda 参数（局部变量类型推断在 10）  
5. 移除 Java EE、CORBA 等模块（迁移注意）  
6. 更强的飞行记录器等运维能力（了解）  

相对 8：更干净的现代 JDK，很多公司从 8→11→17/21。

---

### Q3. Java 17（LTS）

1. **密封类 Sealed Classes**：限制谁可以继承/实现，利于领域建模与模式匹配  
2. 模式匹配进度（instanceof 模式匹配等已可用；switch 模式匹配演进）  
3. 更强的封装：内部 API 默认更难非法访问  
4. 新随机数生成器 API  
5. 废弃/移除旧安全机制路径等（了解）  
6. 持续 GC/性能改进  

适合答「语言表达力 + 封装安全」。

---

### Q4. Java 21（LTS，当前面试重点）

1. **虚拟线程（Virtual Threads）**  
   - 由 JVM 调度的轻量线程，可大量创建  
   - 适合高并发阻塞式 I/O（少改代码，线程数不再是瓶颈）  
   - 注意：不要池化虚拟线程；pinning（在 synchronized 里阻塞）要了解  
2. **Sequenced Collections**：有序集合统一 `getFirst`/`getLast` 等  
3. 模式匹配、Record 模式等增强  
4. 分代 ZGC 等（运维向）  

**和 Go goroutine 对比一句：** 都是轻量并发单元；Java 虚拟线程让「同步代码风格」更容易撑高并发。

### Q5. Java 25 新特性怎么答？

版本发布节奏快，**不要编造具体 JEP 编号若不确定**。稳妥结构：

1. 说明自己跟 **LTS（17/21）** 为主，非 LTS 上线前看官方 Release Notes / JEP  
2. 关注方向：语言持续简化（模式匹配）、Loom 生态（作用域值等）、性能与 GC、API 清理  
3. 若面试时已发布，可准备 2～3 条具名特性（以 oracle.com / OpenJDK 发布说明为准）  

态度分：诚实 + 有升级评估意识，好过背错特性。

### Q6. Optional 详解

- 目的：API 返回值表达「可能无结果」  
- 创建：`of`（非 null）/`ofNullable`/`empty`  
- 使用：`map`/`flatMap`/`filter`/`ifPresent`/`orElse`/`orElseGet`/`orElseThrow`  
- **反模式：** 当字段类型到处传；`optional.get()` 无判断；`orElse(耗时计算)` 应改 `orElseGet`

### Q7. Lambda 表达式、函数式接口、方法引用怎么答？

这题在 Java 8 里很高频，最好拆成三层：**写法是什么、底层依赖什么、实际怎么用**。

#### 1）Lambda 是什么？

Lambda 本质是把「一段行为」当成值传递，常用于回调、集合处理、策略简化。

```java
list.forEach(x -> System.out.println(x));
```

和匿名内部类相比：

- 写法更短  
- 更适合表达「单一行为」  
- 不会额外引入那么重的样板代码

#### 2）函数式接口是什么？

函数式接口：**只有一个抽象方法**的接口，可以用 Lambda 赋值。

```java
@FunctionalInterface
interface MyOp {
    int apply(int a, int b);
}
```

常见内置接口：

| 接口 | 含义 |
| --- | --- |
| `Function<T,R>` | 输入 T，输出 R |
| `Consumer<T>` | 消费 T，无返回值 |
| `Supplier<T>` | 无输入，提供 T |
| `Predicate<T>` | 输入 T，返回布尔 |

#### 3）方法引用是什么？

当 Lambda 只是「转调一个已有方法」时，可写成方法引用。

```java
list.forEach(System.out::println);
```

常见形式：

1. `对象::实例方法`  
2. `类::静态方法`  
3. `类::实例方法`  
4. `类名::new`（构造器引用）

#### 4）底层怎么实现？

不是简单生成匿名内部类字节码，核心依赖：

- `invokedynamic`
- `LambdaMetafactory`

面试基础层不用讲太深，但知道它不是「语法糖等于匿名类」会加分。

#### 5）常见坑

1. Lambda 里访问的局部变量必须是 **effectively final**  
2. 不要为了炫技把简单 for 循环写得很绕  
3. 带副作用的 Lambda 在并行流里尤其要小心

**口述模板：**  
> Lambda 是 Java 8 引入的行为参数化写法，配合函数式接口使用，适合回调、集合处理和策略简化。方法引用是 Lambda 的进一步简写，底层依赖 invokedynamic，不是传统匿名内部类那套实现。

### Q8. Stream API 常用操作有哪些？和 for 循环相比怎么选？

Stream 适合对集合做**声明式流水线处理**，强调「要什么结果」，不是手写每一步遍历细节。

#### 常见操作

| 类别 | 常用方法 |
| --- | --- |
| 创建 | `stream()`、`parallelStream()`、`Stream.of()` |
| 中间操作 | `filter`、`map`、`flatMap`、`distinct`、`sorted`、`limit`、`skip` |
| 终止操作 | `collect`、`forEach`、`count`、`findFirst`、`anyMatch`、`reduce` |

#### 典型例子

```java
List<String> names = users.stream()
    .filter(User::isActive)
    .map(User::getName)
    .sorted()
    .toList();
```

#### 和 for 循环怎么比？

| 维度 | Stream | for 循环 |
| --- | --- | --- |
| 可读性 | 业务规则清晰时更强 | 简单直接，细粒度控制更好 |
| 组合性 | 很强，适合 filter/map/reduce 链 | 复杂组合代码会变啰嗦 |
| 调试 | 链式调用有时不如 for 直观 | 容易逐步断点 |
| 性能 | 一般够用；不是所有场景都更快 | 极致性能/低开销循环有优势 |

#### 使用建议

1. **集合转换、过滤、聚合**很适合 Stream  
2. **需要 break / continue / 下标控制 / 复杂副作用**时，for 循环更稳  
3. 并行流不要乱开，只有数据量大、操作无共享副作用时才考虑

**口述模板：**  
> Stream 适合把集合处理写成过滤、映射、聚合的流水线，代码更声明式；但如果逻辑很依赖副作用、下标控制或提前跳出，for 循环往往更直接。不是所有遍历都该 Stream 化。

### Q9. record、sealed class、模式匹配分别解决什么问题？

这是现代 Java 语法表达力提升的代表，面试时不用背太多 JEP，重点说「解决了什么痛点」。

#### 1）record

适合只承载数据的不可变对象，自动生成构造器、`equals/hashCode/toString`。

```java
public record UserDTO(Long id, String name) {}
```

解决：

- DTO/VO 样板代码太多  
- 数据对象语义不够清晰

#### 2）sealed class

限制谁可以继承某个父类/接口。

```java
public sealed interface Shape permits Circle, Rect {}
```

解决：

- 继承树过于开放  
- 领域模型边界不明确

#### 3）模式匹配

让类型判断 + 转型写得更自然。

```java
if (obj instanceof String s) {
    System.out.println(s.length());
}
```

解决：

- `instanceof` 后还要手动强转，样板代码多  
- `switch`/分支语义不够清晰

**口述模板：**  
> record 解决数据类样板代码，sealed class 解决继承边界过宽，模式匹配解决类型判断和强转啰嗦。它们共同趋势就是让 Java 在保持类型安全的同时，表达更简洁。
