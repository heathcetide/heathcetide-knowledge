#### 18.什么是缓存穿透 ? 怎么解决 ?
缓存穿透就是数据库和Redis里面都没有这个数据然后请求会直接打到数据库，如果有大量这样的请求就会导致数据库被击穿，这种情况也就是缓存击穿
解决这个的法子比较多常见的有两种
1. 缓存空数据的法子: 也就是如果查询到数据库和Redis里面都没有就给Redis缓存空数据，从而下次就会被Redis拦截，不过这种方式会有一定的可能造成数据的短期不一致性不过却是最快的解决方式
2. 布隆过滤器: 使用布隆过滤器的方式在Redis和MySQL之前进行判断，这样就可以提前去过滤掉那些明显的不存在的数据防止直接打到数据库
当然除了这两种方法之外还有很多的方法:
3. 可以增加id的复杂程度防止被直接猜到
4. 添加IP黑白名单的方式进行封禁恶意防止持续访问
5. 添加用户/接口/系统级别的限流处理，从而防止持续被访问攻击
6. 做好权限校验，使用多级缓存这些
#### 19.介绍一下布隆过滤器？
  布隆过滤器主要是用于检索一个元素是否在一个集合中。
  我们当时使用的是 Redisson实现的布隆过滤器。 它的底层主要是先去初始化一个比较大数组，里面存放的二进制0或1。
  在一 开始都是0，当一个key来了之后经过3次hash计算，模于数组长度找到数据 的下标然后把数组中原来的0改为1，这样的话，
  三个数组的位置就能标明一 个key的存在。查找的过程也是一样的。 当然是有缺点的，
  布隆过滤器有可能会产生一定的误判，我们一般可以设置 这个误判率，大概不会超过5%，其实这个误判是必然存在的，要不就得增 加数组的长度，其实已经算是很划分了，5%以内的误判率一般的项目也能 接受，不至于高并发下压倒数据库。

#### 20.什么是缓存击穿 ? 怎么解决 ?
缓存击穿也就是针对热点key的情况，如果一个key的访问量非常大，在其过期的时候就会有大量的请求打过来进行重构缓存有这样大量的key的话就会导致全部访问数据库从而导致数据库MySQL宕机的情况
要解决这个问题方法

1. 使用锁的方式（强一致，性能差），缓存失效时，不立即进行缓存重建，先使用如 Redis 的 setnx 去设置一个互斥锁，当操作成功返回时再进行缓存重建的操作，否则重试方法，其实也就是保证同一时间只有一个key在重构缓存
2. 使用逻辑过期的方法（高可用，性能优），

①：在设置key的时候，设置一个过期时间字段一块存入缓存中，不给当前 key设置过期时间
②：当查询的时候，从redis取出数据后判断时间是否过期
③：如果过期则开通另外一个线程进行数据同步，当前线程正常返回数据， 这个数据不是最新的。

3. 进行**预加载缓存**，预测流量，使用定时任务或者定期更新的方式提前把数据放入到缓存中的方式从而能避免突发流量导致缓存失效时访问数据库
4. 缓存预热与超时保护，也就是在缓存过期之间对缓存进行重构，可以理解为轮训expire时间的方式来帮助重建缓存，防止大量的请求打到数据库。
5. **限流与降级：**
- 当系统流量激增时，除了优化缓存外，也可以通过限流来减少对数据库的压力，或者采取降级策略，返回某些简化版的数据，避免直接冲击数据库。
- **操作**：可以通过 API 网关、负载均衡器等技术来实施流量控制，避免流量过载。


锁的方法适用于需要强一致性的数据，而逻辑判断则无需强一致性。

这里需要注意，如果流量很大打穿了redis然后去压力数据库并不属于缓存击穿，因为缓存击穿强调的是由于key的过期时间导致没有起到防护作用，导致大量的key都访问了数据库试图重建缓存导致出现的问题，由于 Redis 本身无法承载突发的高流量负载导致的宕机其实不算是缓存击穿，不过流量激增会加剧缓存击穿问题的出现

那么不可能等到打崩了再来修的，有没有办法应对呢

##### 流量激增时如何提前防护？

确实，如果是由于流量激增而导致缓存击穿，最好的防护策略是在问题发生之前采取预防措施。以下是几种提前防护的策略：

1. **商品流量预测与动态缓存预热，**对于高阶的系统，通过历史数据分析或者个人用户行为，营销活动去预测高流量商品。然后，根据预测结果预先加载或更新这些商品的缓存。
2. **流量预热与缓存更新**：提前识别出流量可能激增的时刻，并在高峰期前自动更新缓存，避免缓存失效时直接打到数据库。
3. **限流和流量控制**：结合流量控制技术，如令牌桶、漏桶算法等，在流量激增时进行动态调整，避免数据库承受过大压力。
4. **降级机制**：在无法获取最新数据时，尽量返回部分数据，或返回缓存中较老的数据，尽量避免访问数据库。
5. **热点数据缓存分流：** 对于热门商品，可以采用**缓存分流策略**，即为这些高流量商品设置独立的缓存池或者专门的缓存服务器。通过分流，将这些热点商品的数据分布到不同的 Redis 实例或分区中，避免单个缓存节点或 Redis 实例因为高并发访问而崩溃。
6. **异步更新与双缓存策略**
- **异步缓存更新**：当缓存过期或失效时，不立即同步更新缓存，而是先返回部分缓存数据，然后异步后台更新缓存。这样可以确保前端请求能够迅速响应，而不造成过多请求打到数据库。
- **双缓存机制**：采用主缓存和备用缓存策略，主缓存快速读取，备用缓存用于补充和后台同步更新。这能确保即使主缓存失效时，备用缓存也能快速恢复数据。这里一般是本地缓存放在外层，不过这里不可能所有缓存都放在外层，这里可以做一个检测key的用量机制，如果量大就扔到本地缓存中，又快又有保底

7. **实时监控与自动扩展**

- 对于流量突增时，可以通过实时监控系统（如 Prometheus、Grafana 等）跟踪数据库、缓存、网络等各个组件的状态。一旦系统流量激增，监控系统能够实时报警并触发自动扩展机制。
- **自动扩展**：根据流量的变化，动态地扩展缓存层或数据库的处理能力（如自动增加 Redis 实例或数据库节点），确保系统在高流量期间能够扩展资源，避免因资源不足而导致系统崩溃。

8. **利用边缘缓存与CDN**

- 对于电商类应用，利用**CDN**（内容分发网络）和**边缘缓存**可以帮助缓存大量静态内容和商品信息。当流量激增时，通过将部分内容缓存到离用户更近的边缘节点，可以大大减少核心服务器的负担，避免直接访问 Redis 和数据库。

#### 21.什么是缓存雪崩 ? 怎么解决 ?

缓存雪崩主要是指，当有大量缓存同时过期，导致大量请求达到数据库导致数据库挂掉或者因为redis服务器重启导致大量请求达到数据库。

解决方法：如果是由大量缓存数据同时过期导致的，可以给数据的过期时间加上一个随机值，比如可以在原有的失效时间基 础上增加一个随机值，比如1-5分钟随机，这样每一个缓存的过期时间的重 复率就会降低，就很难引发集体失效的事件

针对 Redis 服务不可用的情况：解决redis宕机问题）：

1.用加锁或者队列的方式保证来保证不会有大量的线程对数据库一次性进行读写，从而避免失效时大量的并发请求落在了底层存储系统上。
2.采用 Redis 集群，避免单机出现问题整个缓存服务都没办法使用。（哨兵模式，集群模式）
3.限流，避免同时处理大量的请求。（给缓存业务添加降级限流的策略，使用nginx或者springcloud gateway）
4.多级缓存，例如本地缓存+Redis 缓存的组合，当 Redis 缓存出现问题时，还可以从本地缓存中获取到部分数据。（Guava或者caffeine）

针对热点缓存失效的情况：
1.缓存永不失效（不太推荐，实用性太差）。
2.缓存预热，也就是在程序启动后或运行过程中，主动将热点数据加载到缓存中。
3.（解决同一时间大量失效问题）缓存失效时间分散开，比如我们可以在原有的失效时间的基础上增加一个随机值，比如一到五分钟随即，这样每一个缓存的过期时间的重复率都会降低，这样就很难引发集体失效的事件。TTL添加随机值。

#### 22.Redis做为缓存，MySQL的数据如何与Redis进行同步呢？（双写一致性）

一定要先介绍自己的业务背景（比如需要高一致性要求，允许延迟一致）

采用的阿里的canal组件实现数据同步：不需要更改业务代码，部署 一个canal服务。canal服务把自己伪装成mysql的一个从节点，当mysql数据 更新以后，canal会读取binlog数据，然后在通过canal的客户端获取到数据， 更新缓存即可。

采用的是redisson实现的读写锁，在读的时候添加共享锁，可以保证读 读不互斥，读写互斥。当我们更新数据的时候，添加排他锁，它是读写，读 读都互斥，这样就能保证在写数据的同时是不会让其他线程读数据的，避免 了脏数据。这里面需要注意的是读方法和写方法上需要使用同一把锁才行。

共享锁: 读锁readlock，加锁之后其他线程可以共享读操作。

在使用 Redis 作为缓存时，通常会面临 **双写一致性** 问题，即如何保证数据库（MySQL）与缓存（Redis）中的数据保持同步，确保两者的数据一致性。为了处理这个问题，常用的策略包括：

**1. 缓存更新策略（Write-Through 或 Write-Behind）**
这两种策略在一定程度上能保持缓存和数据库的数据一致性。
- **Write-Through 缓存**：
- 每次更新数据库时，缓存会立即更新。
- 当你更新数据库中的数据时，会同步将更新的数据写入缓存。这确保了缓存和数据库的数据一致性，但可能会带来性能上的一些开销。
- 适用于数据更新频繁且一致性要求较高的场景。
- **Write-Behind 缓存**：
- 这种策略会先更新缓存，再异步地将更新操作写入数据库。更新操作不会等待数据库更新完成，缓存更新后立即返回结果，数据库会在后台批量处理更新。
- 适用于某些性能要求较高的场景，但需要特别关注写入数据库的延迟和失败问题。

**2. 缓存失效策略（Cache Aside）**
- **缓存穿透**：如果缓存中没有数据，直接查询数据库并将结果存入缓存。下一次请求则从缓存获取。
- **缓存更新**：当数据发生更新时（如插入、更新、删除），需要同步更新缓存。常见的做法是：
- 删除缓存，确保下一次查询时会从数据库重新加载。
- 更新缓存，使其与数据库保持一致。
**典型步骤：**
- 当用户请求数据时，先查询缓存，如果缓存中有，则直接返回；如果没有，则查询数据库。
- 查询数据库后，将数据更新到缓存中。
- 数据更新时（比如通过 `INSERT` 或 `UPDATE`），先更新数据库，然后删除相关缓存（或更新缓存）。
这种方式的缺点是数据更新时需要进行两次操作，可能会出现短时间内数据不一致的情况，特别是在高并发的情况下。

**3. 异步更新与延时双删**
由于缓存更新和数据库更新通常是两个独立操作，可能会存在**短时间的不一致**。为解决此问题，可以采用“延时双删”策略。
**延时双删**策略：
- 第一次删除缓存：在数据更新时，首先删除缓存数据。
- 更新数据库：更新数据库中的数据。
- 延时再次删除缓存：在一段时间后，再次删除缓存。这样做的目的是防止由于某些延迟或问题导致缓存的数据仍然不一致。
延时双删策略可以减少缓存和数据库之间的数据不一致的时间窗口。

**4. 消息队列与异步同步**
通过使用消息队列（如 Kafka、RabbitMQ 等）进行异步更新同步：
- 当数据库中的数据发生变化时，先将变更操作记录到消息队列中。
- 通过消费者异步处理队列中的消息，及时同步缓存。
这种方式可以确保缓存的更新是基于数据库的变更，避免了数据库和缓存之间的数据不一致情况。

**5. 基于时间戳的版本号控制**
对于数据的缓存，可以采用版本号（或时间戳）策略。每次更新数据库时，都会更新版本号或时间戳。缓存中存储的是带有版本号的数据。
**具体做法：**
- 数据库表中的每条记录都附带一个版本号字段。
- 当从缓存获取数据时，先检查缓存中的版本号，如果版本号与数据库中的不一致，则重新从数据库加载数据并更新缓存。
- 更新数据库时，确保同时更新数据库中的版本号或时间戳，缓存的数据会根据版本号来判断是否需要更新。

**6. 使用 Redis 的数据过期策略**
为避免缓存过期时出现数据不一致，可以通过设置缓存的过期时间来减少这种情况的影响。虽然缓存过期后仍需查询数据库，但如果设计合理，缓存的过期时间应能满足大多数访问场景，避免频繁访问数据库。

**7. 乐观锁与分布式锁**
在一些高并发的系统中，使用乐观锁或分布式锁来保证更新时缓存与数据库的双写一致性：
- **乐观锁**：在更新数据库时使用版本号或时间戳来确保没有其他线程在更新同一数据，防止缓存不一致。
- **分布式锁**：如果有多个进程或者线程需要同时操作缓存和数据库，可以使用分布式锁（如 Redis 的 `SETNX`）来保证同一时间只有一个进程进行缓存和数据库的写操作。
