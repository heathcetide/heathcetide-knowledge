#### 23.redis做为缓存，数据的持久化是怎么做的？
Redis中提供了两种数据持久化的方式：1、RDB 2、AOF
持久化机制：1.RDB（redis Data Base）。2.AOF(Append only File)增量日志。3.混合持久化：RDB + AOF
1. RDB（Redis Database Backup file (Redis数据备份文件，也叫Redis数据快照)）是一个快照文件，它是把redis内存存储的数据写到磁盘上，当 redis实例宕机恢复数据的时候，（从磁盘中读取快照文件，恢复数据）方便从RDB的快照文件中恢复数据。
	具体操作：可以使用Redis的save命令或者bgsave命令手动执行RDB（save是由主线程来执行RDB，会阻塞所有的命令，bgsave是开启子线程执行RDB，避免主进程收到影响，Redis内部有触发RDB的机制，可以在redis.conf文件中找到，格式如下： save 900 1 {900s内，如果至少有一个key被修改，则执行bgsave}）

RDB的执行原理：
bgsave开始时会fork主进程得到子进程，子进程共享主进程的内存数据，完成fork后读取内存数据并且写入RDB文件。

这里有一些细节，也就是for主进程之后的子进程，它共享了主进程的内存数据，它会写新的RDB文件，并且会替代旧的RDB文件，但是这里有一些问题，比如数据在RDB保存的时候，它如果改变了怎么办？这里用了一些技术，也就是在fork主进程的时候使用了copy-on-write技术，它将物理内存中的数据进行了锁定，变成了read-only，也就是只能读取不能写入。

copy-on-write：
1.当主进程执行读操作的时候，访问共享内存
2.当主进程执行写操作的时候会拷贝一份数据，执行写操作

2. AOF（append only file）的含义是追加文件，当redis操作的每一个写命令的时候，都会存储这个文件中（可以看作是命令日志文件）， 当redis实例宕机恢复数据的时候，会从这个文件中再次执行一遍命令来恢复 数据。
Redis的AOF默认是关闭的，需要修改redis.conf配置文件来开启AOF
也就是appendonly yes （这里默认为no）
#AOF文件的名称： appendfilename "appendonly.aof"

这里还可以设置AOF命令的记录频率，可以通过redis.conf配置
**appendfsync always #每执行一次写命令，就立即记录到AOF文件（可靠性很高，但是性能影响很大）**
**appendfsync everysec #表示每隔一秒就将缓冲区数据写到AOF文件，是默认方案（性能适中，最多丢失1s数据）**
**appendfsync no #写命令执行完先放缓冲区，由操作系统决定何时将缓冲区内容写到磁盘（性能很好，可靠性很差，可能丢失大量数据）**
AOF：因为是记录命令，AOF文件会比RDB大得多，而且AOF会记录对同一个key的多次写操作，但是只有最后一次写操作才有意义，通过执行bgrewriteaof命令，可以让AOF文件执行重写功能，用最少的命令达到相同的效果。
Redis也会在触发阈值的时候自动去重写AOF文件，阙值也可以在redis.conf中配置：
#AOF文件比上次文件增长超过多少百分比则触发重写
auto-aof-rewrite-percentage 100
#AOF文件体积最小多大以上才会触发重写
auto-aof-rewrite-min-size 64mb
##### 这两种方式，哪种恢复的比较快呢？

RDB因为是二进制文件，在保存的时候体积也是比较小的，它恢复 的比较快，但是它有可能会丢数据，我们通常在项目中也会使用AOF来恢复 数据，虽然AOF恢复的速度慢一些，但是它丢数据的风险要小很多，在AOF 文件中可以设置刷盘策略，我们当时设置的就是每秒批量写入一次命令


#### 24.数据库有1000万数据 ,Redis只能缓存20w数据, 如何保证Redis中的 数据都是热点数据 ?

可以使用 allkeys-lru （挑选最近最少使用的数据淘汰）淘汰策略，那留下来 的都是经常访问的热点数据

#### 25.Redis的内存用完了会发生什么？

这个要看redis的数据淘汰策略是什么，如果是默认的配置，redis内存 用完以后则直接报错。我们当时设置的 allkeys-lru 策略。把最近最常访问的 数据留在缓存中
