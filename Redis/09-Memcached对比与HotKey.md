# Redis · 09-Memcached对比与HotKey

#### 47.Redis和Memcached有哪些区别？

回答：

**数据结构上：**

Redis支持多种数据结构如：String，list，set，zset，hash等，适合存储复杂的数据类型

Memcached：仅支持简单的键值对存储，数据结构较为单一

**从持久化上：**

Redis支持持久化功能，可以将数据保存在磁盘上，通过RDB和AOF两种方式实现数据的持久化

Memcached：不支持数据持久化，重启之后数据会丢失，适合临时数据存储

**从分布式架构上:**

Redis: 内置支持主从复制和集群分片，能在分布式环境中提供高可用性和扩展性.

Memcached:没有内置分片支持，需要在客户端代码中实现分布式逻辑

**从功能上：**

Redis; 支持发布订阅，Lua脚本等特性

Memcached： 特性较少

**内存管理：**

Redis: 使用高效的内存管理算法，支持内存回收策略，如（LRU，LFU，TTL）来管理内存使用

Memcached使用slab分配器管理内存，以避免内存碎片，但对内存使用的控制不如Redis灵活

|**适用场景**|大规模分布式系统、高并发、高实时性需求，复杂的缓存和数据库一致性需求|适合简单的缓存更新场景|对实时性要求不高的场景|

**Binlog 监听** 方案虽然有很多优点，但也存在一些缺点和挑战。以下是使用 **Binlog 监听** 方案时需要注意的缺点：

**1. 系统复杂性增加**

- **配置与维护**：Binlog 监听需要额外的基础设施和配置，如 Canal 或 Debezium 等工具，这增加了系统的复杂度。你需要配置监听器、数据同步组件，且需要处理这些工具的运行和更新。
- **异常处理**：Binlog 监听系统中涉及多个组件（如数据库、Binlog 解析、缓存更新），在遇到故障时需要复杂的错误处理机制，以确保系统能继续运行。

**2. 延迟问题**

- **数据同步延迟**：虽然 Binlog 监听是异步的，但在数据库变更到实际更新缓存之间仍然会有一定的延迟，特别是在高负载的情况下，数据的更新可能会受到队列处理或网络延迟的影响。对于要求实时一致性的应用，延迟可能无法接受。
- **缓存过期问题**：Binlog 监听机制并不能立即同步缓存，所以可能会导致短时间的缓存不一致。例如，如果数据库数据已更新，但相应的缓存尚未更新，用户可能会读取到过期数据。

**3. 性能开销**

- **监听 Binlog 的性能消耗**：监听 Binlog 本身会消耗一定的计算和网络资源，尤其是当数据库表发生大量变更时，Binlog 监听系统需要频繁处理这些变更并更新缓存。高频的 Binlog 事件会导致监听器系统的资源消耗增加。
- **网络传输**：如果 Binlog 监听系统和 Redis 缓存位于不同的数据中心或网络环境中，Binlog 事件的传输延迟会增加，可能导致缓存更新的延迟。

**4. 复杂的回滚和错误恢复**

- **数据丢失和回滚**：在一些特殊情况下（例如 Canal 或 Debezium 失效、Binlog 事件丢失、系统崩溃等），可能会导致缓存与数据库的数据不一致。而且，Binlog 监听器通常是单向同步的，恢复过程较为复杂，涉及到如何从数据库或日志中恢复丢失的数据。
- **操作的幂等性**：由于 Binlog 监听是异步的，可能会出现重复消费的情况，这会导致缓存中的数据被重复更新或出现错误。需要确保每个操作是幂等的（即无论执行多少次，结果都是一致的）。

**5. 不适用于某些操作类型**

- **非 DML 变更**：Binlog 监听器主要用于监控 DML（数据操作语言）事件，如 `INSERT`、`UPDATE`、`DELETE`，但对于某些数据库变更（例如 DDL 操作，数据库结构变动）并不适用。这意味着在一些数据库结构变更的场景下，Binlog 监听可能无法捕捉到所有重要的更新。
- **高频更新的效率问题**：在处理频繁的小数据变更时，Binlog 监听可能会受到性能瓶颈影响。如果同一条数据频繁更新，导致多个变更事件频繁触发缓存更新，可能会对系统性能产生不利影响。

**6. 依赖性和稳定性**

- **依赖于 Binlog**：Binlog 监听方案依赖于 MySQL 或其他数据库的 Binlog 配置，数据库的正确配置对于整个方案至关重要。如果 Binlog 配置不正确，或者数据库版本不兼容，可能导致数据同步失败。
- **外部工具的可靠性**：像 Canal 和 Debezium 等工具虽然非常强大，但它们也可能面临兼容性、稳定性或性能瓶颈问题。如果这些工具出现故障，整个缓存更新系统就可能失效，因此需要额外的监控和维护工作。

**7. 维护和扩展难度**

- **监控与调优**：Binlog 监听方案需要实时监控系统的健康状态，尤其是在高并发和大数据量的场景下。需要为 Binlog 监听系统、Redis 缓存系统和数据库的负载进行调优，确保它们能够高效地工作。
- **跨数据库和分库分表的复杂性**：在分布式环境下，尤其是跨多个数据库和多个数据中心的情况下，Binlog 监听可能会面临更复杂的数据同步问题。需要特殊设计和额外的同步机制来处理跨数据库或分表的情况。

**8. 一致性问题**

- **最终一致性**：Binlog 监听是一种基于事件的异步更新机制，因此它天然是最终一致性的，而不是强一致性。在数据库数据变动后，缓存的更新可能会有延迟，这意味着在短时间内，缓存和数据库的数据可能会不一致，直到异步更新完成。

#### 48.什么是HotKey？
如果一个 key 的访问次数比较多且明显多于其他 key 的话，那这个 key 就可以看作是 hotkey（热 Key）。例如在 Redis 实例的每秒处理请求达到 5000 次，而其中某个 key 的每秒访问量就高达 2000 次，那这个 key 就可以看作是 hotkey。  

hotkey 出现的原因主要是某个热点数据访问量暴增，如重大的热搜事件、参与秒杀的商品。  

### 59.hotkey有什么危害？

处理 hotkey 会占用大量的 CPU 和带宽，可能会影响 Redis 实例对其他请求的正常处理。此外，如果突然访问 hotkey 的请求超出了 Redis 的处理能力，Redis 就会直接宕机。这种情况下，大量请求将落到后面的数据库上，可能会导致数据库崩溃。  

因此，hotkey 很可能成为系统性能的瓶颈点，需要单独对其进行优化，以确保系统的高可用性和稳定性。  

### 60.如何发现hotKey？

1、使用 Redis 自带的 --hotkeys 参数来查找。

- Redis 4.0.3 版本中新增了 hotkeys 参数，该参数能够返回所有 key 的被访问次数。
- 使用该方案的前提条件是 Redis Server 的 maxmemory-policy 参数设置为 LFU 算法，不然就会出现错误。
- Redis 中有两种 LFU 算法：
- volatile-lfu（least frequently used）：从已设置过期时间的数据集（server.db[i].expires）中挑选最不经常使用的数据淘汰。
- allkeys-lfu（least frequently used）：当内存不足以容纳新写入数据时，在键空间中，移除最不经常使用的 key。

2、使用MONITOR 命令。

3、借助开源项目。  
京东零售的 [https://gitee.com/jd-platform-opensource/hotkey](https://gitee.com/jd-platform-opensource/hotkey)这个项目不光支持 hotkey 的发现，还支持 hotkey 的处理

4、根据业务情况提前预估。  
可以根据业务情况来预估一些 hotkey，比如参与秒杀活动的商品数据等。不过，我们无法预估所有 hotkey 的出现，比如突发的热点新闻事件等。

5、业务代码中记录分析。  
在业务代码中添加相应的逻辑对 key 的访问情况进行记录分析。不过，这种方式会让业务代码的复杂性增加，一般也不会采用。

6、借助公有云的 Redis 分析服务。  
如果你用的是公有云的 Redis 服务的话，可以看看其是否提供了 key 分析功能（一般都提供了）。
