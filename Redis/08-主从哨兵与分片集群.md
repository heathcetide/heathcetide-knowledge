#### 39.介绍一下主从同步

是这样的，单节点Redis的并发能力是有上限的，要进一步提 高Redis的并发能力，可以搭建主从集群，实现读写分离。一般都是一主多从，主节点负责写数据，从节点负责读数据，主节点写入数据之后，需要把 数据同步到从节点中
  

#### 40.能说一下，主从同步数据的流程吗？

主从同步分为了两个阶段，一个是全量同步，一个是 增量同步 全量同步是指从节点第一次与主节点建立连接的时候使用全量同步，流程是 这样的：

**{全量同步：**

**1.从节点请求主节点同步数据（replication id， offset）**

**2.主节点判断是否是第一次请求，是第一次就与从节点同步版本信息（replication id 和offset）**

**3.主节点执行bgsave，生成RDB文件之后，发送给从节点去执行**

**4.在RDB生成执行期间，主节点会以命令的方式记录到缓冲区（一个日志文件）**

**5.把生成之后的命令日志发送给从节点进行同步}**

**{增量同步：**

**1.从节点请求主节点同步数据，主节点判断不是第一次请求，不是第一次就获取从节点的offset的值**

**2.主节点从命令日志中获取offset值之后的数据，发送给从节点进行数据同步。}**

第一：从节点请求主节点同步数据，其中从节点会携带自己的replication id 和offset偏移量。

第二：主节点判断是否是第一次请求，主要判断的依据就是，主节点与从节 点是否是同一个replication id，如果不是，就说明是第一次同步，那主节点 就会把自己的replication id和offset发送给从节点，让从节点与主节点的信息 保持一致。

第三：在同时主节点会执行bgsave，生成rdb文件后，发送给从节点去执 行，从节点先把自己的数据清空，然后执行主节点发送过来的rdb文件，这 样就保持了一致 当然，如果在rdb生成执行期间，依然有请求到了主节点，而主节点会以命 令的方式记录到缓冲区，缓冲区是一个日志文件，最后把这个日志文件发送 给从节点，这样就能保证主节点与从节点完全一致了，后期再同步数据的时 候，都是依赖于这个日志文件，这个就是全量同步 增量同步指的是，当从节点服务重启之后，数据就不一致了，所以这个时 候，从节点会请求主节点同步数据，主节点还是判断不是第一次请求，不是 第一次就获取从节点的offset值，然后主节点从命令日志中获取offset值之后 的数据，发送给从节点进行数据同步

  

#### 41.怎么保证Redis的高并发高可用？

首先可以搭建主从集群，再加上使用redis中的哨兵模式，哨兵模式 可以实现主从集群的自动故障恢复，里面就包含了对主从服务的监控、自动 故障恢复、通知；如果master故障，Sentinel会将一个slave提升为master。 当故障实例恢复后也以新的master为主；同时Sentinel也充当Redis客户端的 服务发现来源，当集群发生故障转移时，会将最新信息推送给Redis的客户 端，所以一般项目都会采用哨兵的模式来保证redis的高并发高可用。

#### 42.你们使用Redis是单点还是集群，哪种集群？

当时使用的是主从（1主1从）加哨兵。一般单节点不超 过10G内存，如果Redis内存不足则可以给不同服务分配独立的Redis主从节 点。尽量不做分片集群。因为集群维护起来比较麻烦，并且集群之间的心跳 检测和数据通信会消耗大量的网络带宽，也没有办法使用lua脚本和事务。

#### 44.redis的分片集群有什么作用？

分片集群主要解决的是，海量数据存储的问题，集群中有多个 master，每个master保存不同数据，并且还可以给每个master设置多个slave 节点，就可以继续增大集群的高并发能力。同时每个master之间通过ping监 测彼此健康状态，就类似于哨兵模式了。当客户端请求可以访问集群任意节 点，最终都会被转发到正确节点。

#### 45.Redis分片集群中数据是怎么存储和读取的？

在Redis集群中是这样的 Redis 集群引入了哈希槽的概念，有 16384 个哈希槽，集群中每个主节点绑 定了一定范围的哈希槽范围， key通过 CRC16 校验后对 16384 取模来决定放 置哪个槽，通过槽找到对应的节点进行存储。 取值的逻辑是一样的

1. 请简单介绍一下 Redis 集群的工作原理。

- Redis 集群采用去中心化的架构，没有中心节点。它将数据分成 16384 个哈希槽（hash slot），每个节点负责一部分哈希槽。当客户端发送一个键值对操作请求时，Redis 会根据键的 CRC16 算法计算出一个哈希值，然后对 16384 取模，得到这个键对应的哈希槽编号。然后将请求转发到负责这个哈希槽的节点上进行处理。
- 节点之间通过 Gossip 协议进行通信，用于节点发现、故障检测等。例如，当一个新节点加入集群时，它会通过 Gossip 协议与其他节点交换信息，让其他节点知道它的存在，并且重新分配哈希槽。当一个节点出现故障时，其他节点也可以通过 Gossip 协议感知到，并进行数据的重新分配。

2. 请描述一下 Redis 集群中的主从复制是如何工作的？

- 在 Redis 集群的主从复制中，主节点（Master）负责接收客户端的写操作请求，并将数据的变更记录到自己的内存中。从节点（Slave）会主动连接主节点，并向主节点发送 SYNC 命令。
- 主节点收到 SYNC 命令后，会开始在后台进行数据备份，将当前数据集的快照发送给从节点，从节点在接收到快照后，会将其加载到自己的内存中。之后，主节点会将在备份期间接收到的新的写操作命令发送给从节点，从节点会执行这些命令，以保持与主节点的数据同步。
- 主从复制可以用于数据备份、读写分离等场景。例如，读操作可以在从节点上进行，以分担主节点的压力。并且，在主节点出现故障时，从节点可以被提升为新的主节点，以保证系统的可用性。

#### **46.拆分热点 key 的原因**
将热点 key 拆分成多个 key 并分布到多个 Redis 实例的本质，是为了缓解**单 key 被频繁访问**带来的单点性能问题。

#### **场景：为什么要拆分热点 key？**

- **热点 key = 单点瓶颈**：

- 在 Redis 集群模式下，单个 key 始终会被分配到固定的一个分区（分片）。
- 即使有 Redis 集群，多次访问热点 key 依然会落在相同节点，导致单个节点压力过大。

- **拆分后解决问题**：

- 将一个热点 key 拆分为多个子 key（如 `key-1`, `key-2`），每个子 key 分配到不同的 Redis 节点，从而分散单个节点的压力。

#### **举例说明**：

假设秒杀活动中一个商品的库存存储在 `item-123-stock` 中：

- 每秒有 10w 次请求都访问这个 key，Redis 集群中的某个分区（节点）因此过载。
- 解决方案：将 `item-123-stock` 拆分为 `item-123-stock-1`, `item-123-stock-2`, `item-123-stock-3`，每个子 key 存储库存的一部分，请求通过 hash 算法分散到多个 key，降低单节点的压力。

**注意**：拆分适用于访问量非常集中的单 key 场景，对于普通热点数据（非极端访问量），更推荐优化其他方面。

  

### **51.Redis 集群是否可以缓解热点 key 的压力？**

**Redis 集群可以解决某些热点场景，但无法完全缓解单 key 问题**：

- **优点**：

- Redis 集群可以将 key 分布到多个节点中，从而分散整体流量。
- 当 key 分布相对均匀时，集群模式可以很好地均衡负载。

- **缺点**：

- Redis 集群按 key 的哈希值分片，单个 key 始终路由到一个固定分区。如果某个 key 的访问量特别大（热点 key），依然会造成该分区过载。
- 此时，即便集群有多个节点，也无济于事。
