# Redis · 05-分布式锁

---

#### 26.Redis分布式锁如何实现 ?

（分布式锁的使用场景:集群情况下的定时任务，抢单，幂等性场景）如果只是实现锁的话，如果是单体架构项目的话使用synchronized就没有问题，但是如果是分布式项目就不一样了，因为synchronized针对的范围是jvm，而服务集群的情况下是一个服务多个端口8080，8081这种，每个服务的JVM是不一样的，也就是synchronized出现了问题。所以我们需要分布式锁。

在redis中提供了一个命令setnx(SET if not exists) 由于redis的单线程的，用了命令之后，只能有一个客户端对某一个key设置 值，在没有过期或删除key的时候是其他客户端是不能设置这个key的。

```
获取锁： set lock value nx ex 10   #添加锁，nx是互斥，ex是设置超时时间
释放锁： del key #释放锁，删除即可

这里锁要设置时间，不然可能会造成死锁
```

#### 27.如何控制Redis实现分布式锁有效时长呢？

**（比如setnx的命令执行之后，业务的流程用时超过了setnx的超时时间，这个就会出现问题，如果用setnx的话，我们可以1.根据业务执行时间的预估（但是出现了网络卡顿和抖动，其实是很不好控制的）2.给锁续期，监听执行时长进行操作（其实redisson实现的分布式锁就可以实现这点。值得一提的是其中的加锁，设置过期时间等操作都是基于lua脚本实现的（可以保证redis多条命令实现的原子性）））**

redis的setnx指令不好控制这个问题，我们当时采用的 redis的一个框架redisson实现的。在redisson中需要手动加锁，并且可以控制锁的失效时间和等待时间，当锁住的一个业务还没有执行完成的时候，**（**在redisson中引入了一个WatchDog看门狗机制，就是说每隔一段时间就检查当前业务是否还持有锁，如果持有就增加加锁的持有时间，当业务执行完成之后需要使用释放锁就可以了**）** 还有一个好处就是，在高并发下，一个业务有可能会执行很快，先客户1持 有锁的时候，客户2来了以后并不会马上拒绝，它会自旋不断尝试获取锁， 如果客户1释放之后，客户2就可以马上持有锁，性能也得到了提升。

#### 28.Redisson实现的分布式锁是可重入的吗？
是可以重入的（如果是同一个线程是可以重入的，如果不是同一个线程就没办法重入了）。这样做是为了避免死锁的产生。这个重入其实 在内部就是判断是否是当前线程持有的锁，如果是当前线程持有的锁就会计 数，如果释放锁就会在计算上减一。在存储数据的时候采用的hash结构，大 key可以按照自己的业务进行定制，其中小key是当前线程的唯一标识，value 是当前线程重入的次数

#### 29.Redisson实现的分布式锁能解决主从一致性的问题吗？

**（一般来说会有redis的集群，也就是以一个redis作为主节点，另外两个作为从节点，然后一个从节点读数据，一个从节点写数据，这里两个都是需要同步数据的）**

**不能解决，（**比如，当线程1加锁成功后，master节点数据会异 步复制到slave节点，此时当前持有Redis锁的master节点宕机，slave节点被 提升为新的master节点，假如现在来了一个线程2，再次加锁，会在新的 master节点上加锁成功，这个时候就会出现两个节点同时持有一把锁的问 题。 **）**我们可以利用redisson提供的红锁来解决这个问题，它的主要作用是，不能 只在一个redis实例上创建锁，应该是在多个redis实例上创建锁，（创建公式n/2+1，n是节点的数量）并且要求在 大多数redis节点上都成功创建锁，红锁中要求是redis的节点数量要过半。这 样就能避免线程1加锁成功后master节点宕机导致线程2成功加锁到新的 master节点上的问题了。 但是，如果使用了红锁，因为需要同时在多个节点上都添加锁，性能就变的 很低了，并且运维维护成本也非常高，所以，我们一般在项目中也不会直接 使用红锁，并且官方也暂时废弃了这个红锁（实现复杂，性能差，运维繁琐）

  

#### 30.那么如果业务非要保证数据的强一致性，这个该怎么解决呢？
（Redis是AP思想的，强调高可用，zookeepker是CP思想，如果用zookeeper实现就可以保证强一致性）

redis本身就是支持高可用的，做到强一致性，就非常影响性 能，所以，如果有强一致性要求高的业务，建议使用zookeeper实现的分布 式锁，它是可以保证强一致性的
