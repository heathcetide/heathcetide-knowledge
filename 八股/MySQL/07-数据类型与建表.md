## 面试题

### Q1. 三大范式？

1. **1NF：** 列原子不可再分  
2. **2NF：** 非主属性全依赖主键（消除部分依赖）  
3. **3NF：** 非主属性不传递依赖非主属性  

实战常 **反范式**（冗余）换查询性能，需权衡一致性。

---

### Q2. int(11) 的 11 表示什么？

**不是**存储长度上限。对整数是**显示宽度**（配合 `ZEROFILL`），占空间仍由类型决定（INT 4 字节）。  
面试答：显示宽度，别误会成位数限制。

### Q3. varchar vs char？VARCHAR(100) vs VARCHAR(10)？

最核心的区别就是CHAR定长,VARCHAR变长。

CHAR(10)不管你存几个字符,都固定占10个字符的空间,不够的用空格填充。
VARCHAR(10)存多少占多少,另外再花1~2个字节记录实际长度。

| | CHAR | VARCHAR |
| --- | --- | --- |
| 存储 | 定长补齐 | 变长 + 长度前缀 |
| 适合 | 固定短码 | 变长字符串 |

`VARCHAR(100)` 与 `(10)`：**磁盘按实际长度存**（+1/2 字节长度），但：

- 最大长度影响内存临时表/排序时的分配估算  
- 业务约束不同：100 允许更长输入  
- InnoDB 索引前缀长度、行大小限制要算进去  


什么时候用CHAR
别看CHAR好像很鸡肋,在特定场景下还是有优势的:
1. 存储固定长度的编码,比如ISO国家代码 CHAR(2)、MD5摘要 CHAR(32)、UUID去掉横杠后 CHAR(32)
2. 存储单字符的状态标记,比如性别 CHAR(1)存M/F
3. 频繁更新的短字段,CHAR不会产生碎片,VARCHAIR长度变化可能导致页分裂

提问:VARCHAR(50)和VARCHAR(200)存同样的字符串,占用空间一样吗?

回答:实际存储空间是一样的,都是按实际字符数加1~2字节长度信息。但定义的长度会影响内存分配,MySQL在做排序、JOIN等操作时会按最大长度预分配内存,所以VARCHAIR(200)会比VARCHAR(50)多占内存,影响 sort_buffer能放的行数,间接影响排序性能。

提问:InnoDB存CHAR一定是固定大小吗?
详细解答可以看:MySQL中varchar和char有什么区别?
回答:当使用utf8这类变长字符集时,InnoDB会把CHAR当变长存储。比如CHAR(10)用utf8,每个字符1~3字节,如果按最大30字节固定存储太浪费,所以InnoDB优化成按实你字节数存。只有latin1这种单字节字符集,CHAR才真正定长存储。

提问:VARCHAR长度超过多少会存到行外?
回答:这取决于行格式。在旧版Compact/Redundant格式下,若单字段长度超过768字节,InnoDB会把超出部分存到溢出页,行内只保留768字节前缀加一个指向溢出页的指针。而在现代默认的Dynamic/Compressed格式下,触发机制不再针对单一字段的固定长度,而是遵循"最长字段优先"原则:为为了保证一个InnoDB页至少能容纳两行数据(即整行总长度不超过约8000字节),最长的字段会被优先选中并整块移至至行外,行内仅保留20字节指针。也就是即便字段不到768字节,若整行太宽也可能溢出。

### Q4. DATETIME vs TIMESTAMP？

| | DATETIME | TIMESTAMP |
| --- | --- | --- |
| 范围 | 更大（'1000'…'9999'） | 受 32 位时间戳限制（8.0.13+ 有改进但仍常谈旧限制） |
| 时区 | 原样存 | 转 UTC 存，取时按时区 |
| 空间 | 5~8B（版本） | 4~7B |

选：要时区敏感常用 TIMESTAMP；要历史远古/未来宽范围用 DATETIME。

---

### Q5. TEXT 最大多长？金额用什么？AUTO_INCREMENT 到最大值？

- **TEXT：** TINYTEXT 255；TEXT 64KB；MEDIUMTEXT 16MB；LONGTEXT 4GB（另有行内前缀+溢出页）  
- **金额：** `DECIMAL(m,n)`，禁止用 FLOAT/DOUBLE  
- **自增到顶：** 再插入报 **Duplicate / out of range**，不会静默回绕（除非改属性）；应监控并换 `BIGINT`

---

### Q6. 一张表最多多少列？建表注意？不存大图片音视频？

- 硬限制约 **4096 列**，但行大小（约 65535 字节等）更紧；实战远小于此。  
- **建表：** 选对类型；主键短；必要索引；字符集 utf8mb4；注释；预留字段谨慎；冷热/大字段拆表。  
- **大媒体：** 库膨胀、备份恢复慢、BP 污染；应对象存储 + 库存 URL。

### Q7. 逻辑删除 vs 物理删除？逻辑外键 vs 物理外键？

| | 逻辑删 `deleted=1` | 物理 `DELETE` |
| --- | --- | --- |
| 可恢复 | 易 | 难（靠备份） |
| 唯一键 | 需处理「软删后可再插」 | 直接释放 |
| 查询 | 都要带条件 | 干净 |

| | 物理外键 | 逻辑外键（应用保证） |
| --- | --- | --- |
| 一致性 | DB 强制 | 应用负责 |
| 性能/分库 | 级联锁、难拆库 | 灵活 |
| 生产 | 互联网常逻辑外键 | 推荐说清权衡 |

阿里手册倾向应用层约束，避免跨库外键。

---

### Q8. 视图？游标？用过哪些函数？

- **视图：** 虚拟表/保存查询；简化权限与复杂 SQL；注意更新限制与性能。  
- **游标：** 逐行取结果集；过程式、开销大；业务层少用，批处理慎用。  
- **函数举例：** `NOW`/`DATE_FORMAT`、`IFNULL`/`COALESCE`、`CONCAT`、`SUBSTRING`、`COUNT/SUM/AVG`、`IF`、JSON 函数等。

---

### Q9. 相比 Oracle，MySQL 优势？为何不推荐存储过程？

**MySQL：** 免费/生态、运维简单、互联网案例多、复制与中间件成熟、云产品全。  
Oracle：企业特性、优化器、复杂 SQL 工具链深。  

**不推荐存过（阿里手册）：** 难移植、难调试版本管理、拖垮 DB CPU、扩展差；业务逻辑放服务层。
