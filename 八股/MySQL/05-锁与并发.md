# 05 · 锁与并发（详解）

锁题要能区分 **粒度、模式、算法（记录/间隙/Next-Key）**，并和隔离级别、死锁分析连起来。

---

## 面试题

### Q1. MySQL 有哪些锁类型？

**按粒度：**

| 锁 | 说明 |
| --- | --- |
| 全局锁 | `FLUSH TABLES WITH READ LOCK`，整库只读，常用于备份 |
| 表锁 | 显式 `LOCK TABLES`；引擎层还有 **意向锁 IS/IX**（表级，与行锁配合） |
| 行锁 | InnoDB 真正互斥单元：记录锁、间隙锁、Next-Key、插入意向锁 |
| MDL | Server 层元数据锁，保护表结构；DDL 与 DML 互斥 |
表锁和行锁。表锁锁整张表,行锁只锁具体的行,粒度越细并发越高。
行锁又细分为三种:记录锁锁住具体那一行,间隙锁锁住两两条记录之间的空隙防止插入,临键锁是记录锁加间隙锁的组合。

![[Pasted image 20260811130725.png]]

还有几个辅助性质的锁:意向锁用来标记表里有没有行锁,加表锁的时候不用遍历;元数据锁MDL保护表结构,DDL和DML不能同时跑;插入意向锁表示有事务在等着往某个间隙插数据;自增锁保证AUTO_INCREMENT分配不重复。
![[Pasted image 20260811130845.png]]

**按模式：** 共享锁 S（读）、排他锁 X（写）。意向锁表示「下面将有行级 S/X」，避免表锁检查时逐行扫。

**行锁算法（InnoDB）：**

- **Record Lock：** 锁住索引记录  
- **Gap Lock：** 锁住记录之间的间隙，阻止插入（RR 下常见）  
- **Next-Key = Record + Gap：** 锁住记录本身及其前面间隙  
- **插入意向锁：** 插入时在间隙上的一种特殊等待，与 Gap 冲突  

**重要口径：** InnoDB 行锁是锁在 **索引** 上的；没有合适索引时，可能锁更多甚至接近表级效果。

提问:什么情况下会触发表锁而不是行锁?
回答:三种情况。一是查询没走索引,InnoDB只能全表扫扫描,锁就加到所有扫描到的记录上,效果等于表锁。二是显式用LOCK TABLES语句加表锁。三是DDL语句比如ALTER TAIBLE,会加MDL写锁。

提问:两个事务都用间隙锁锁住同一个间隙,会死锁吗?
回答:单纯持有间隙锁不会,因为间隙锁之间不冲突。但如果两个事务各自持有间隙锁,然后都想往对方锁住的间隙里插数据,就会死锁。比如事务A持有(3,5)的间隙锁想插(5,10),事事务B持有(5,10)的间隙锁想插(3,5),互相等着对方释放,死锁触发。

提问:为什么说间隙锁是可重复读级别特有的?
回答:可重复读需要防止幻读,间隙锁就是干这个的。读已提;交级别不需要防幻读,所以间隙锁关闭只保留记录锁,锁范围死锁概率也低。这也是很多互联网公司选择读已提交级别的原因之一。

提问:线上加字段导致查询全部超时,原因是什么?
回答:ALTER TABLE需要拿MDL写锁,如果有长事务持有MDL读锁没释放,ALTER TABLE就一直等。更惨的是后面的查询也要拿MDL读锁,但写锁请求优先级更高,所以后面的查询全都堵在ALTER TABLE后面。解决办法是先干掉长事务,或者用pt-online-schema-change这类工具做无锁DDL。

### Q2. 乐观锁和悲观锁是什么？怎么选？

| | 悲观锁 | 乐观锁 |
| --- | --- | --- |
| 假设 | 冲突多，先锁再改 | 冲突少，先改后校验 |
| DB 手段 | `SELECT … FOR UPDATE` | `version`/`cas` 字段：`UPDATE … WHERE id=? AND version=?` |
| 适合 | 库存扣减强一致、冲突高 | 回复帖、资料编辑等冲突低 |

乐观锁失败要重试或提示用户；悲观锁要注意持锁时间与死锁。
乐观锁和悲观锁是两种并发控制思想,本质区别在于对冲突的预期态度不同。
悲观锁假设冲突一定会发生,所以操作数据前先把锁拿到手,别的事务想动这条数据就得排队等着。MySQL里用SELECT...FOR UPDATE 拿排他锁,用SELECT ... LOCK IN SHAREMODE拿共享锁。拿到锁之后别的事务读写都会被阻塞,直到当前事务提交或回滚才释放。
乐观锁假设冲突很少发生,干脆不加锁,等到真正更新的时候再检查数据有没有被别人改过。通常用一个version字段来实现,读的时候把Version一起读出来,更新的时候在WHERE条件里带上这个version,如果version变了说明被别人改过,更新影响0行,业务层自己决定是重试还是报错。

### Q3. 发生死锁如何解决？如何分析？

**运行时：** InnoDB 有死锁检测，会选回滚代价较小的事务，报 `Deadlock found when trying to get lock`。

**分析：**

```sql
SHOW ENGINE INNODB STATUS\G
-- 看 LATEST DETECTED DEADLOCK
```

看两个事务各自持有/等待的索引记录，找出加锁顺序交叉。

**减少死锁：**

1. **固定加锁顺序**（如都按 id 升序更新）  
2. 短事务；一次锁更少行  
3. 合适索引，避免锁升级/锁太多间隙  
4. 热点更新串行化（队列、分段库存）  
5. 捕获死锁异常 **自动重试**  
6. 评估 RR→RC 降低 Gap 相关死锁（有业务代价）  

常见避免死锁的手段
1. 拆分大事务。事务越大持锁时间越长,死锁概率越高。能拆就拆,快进快出
2. 固定加锁顺序。如果业务上必须同时操作表A和表B,所有地方都先锁A再锁B,循环依赖就不会形成
3. 降低隔离级别。可重复读比读已提交多了间隙锁和临键锁,锁的范围更大。如果业务允许,用读已提交能减少锁冲突
4. 合理建索引。没命中索引的更新会锁全表,几万行数据一锁,和别的事务撞上的概率大增
5. 调整锁等待超时。innodb_lock_wait_timeout默认50秒太长,高并发系统可以调到5-10秒,早点超时早点释放

提问:为什么MySQL选择回滚代价小的事务而不是代价大的?
回答:回滚代价小的事务意味着undo log少、已修改的数据少少,回滚本身更快,对系统冲击更小。回滚大事务可能要花几秒 甚至更久,这段时间锁还是拿着,其他事务还是被阻塞。选小的先回滚,让系统尽快恢复正常。

提问:间隙锁和临键锁跟死锁有什么关系?
回答:间隙锁锁的是索引记录之间的空隙,临键锁是行锁加间隙锁的组合。它们主要出现在可重复读隔离级别下,月用来防止幻读。但锁的范围一大,两个事务锁住相邻间隙然后互相等待插,入的场景就容易发生死锁。典型的比如两个事务都先SELECT...FOR UPDATE锁住一个范围,然后各自往对方锁住的范围里里INSERT,直接死锁。

### Q4. 并发事务带来哪些问题？怎么解决？

脏读 / 不可重复读 / 幻读 → **隔离级别 + MVCC + 行锁/间隙锁**（见 [[04-事务与MVCC]]）。  
丢失更新 → 悲观锁、乐观锁、或单条原子 `UPDATE`。  
写写冲突 → 行锁排队。

---

### Q5. 高并发下如何避免锁竞争？

1. 减少锁范围：精准 WHERE 走索引  
2. 减少持锁时间：逻辑移出事务  
3. 打散热点：分段库存、队列异步扣减  
4. 能缓存则缓存；能幂等则消息重试  
5. 读写分离只解决读，不解决同热点写
