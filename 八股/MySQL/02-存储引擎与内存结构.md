# 02 · 存储引擎与内存结构（详解）

引擎对比要落到 **事务/锁/索引组织**；内存结构要落到 **BP / Change Buffer / Doublewrite / Log Buffer** 各自解决什么问题。

---

## 面试题

### Q1. 存储引擎有哪些？InnoDB 与 MyISAM 区别？

MySQL存储引擎是可插拔的,不同引擎负责数据的存储和读取方式。实际工作中95%以上的场景用的都是InnoDB,面试重点把InnoDB和MyISAM的区别搞清楚就行。
MySQL 8.4版本一共提供了10个引擎,常见的有这几个:
1. InnoDB:MySQL 5.5之后的默认引擎,支持事务、行级锁、外键,MVCC也有,适合高并发的OLTP场景。数据按聚簇索引组织,主键查询贼快。
2. MyISAM:老版本的默认引擎,不支持事务,只有表级锁,但读性能不错。适合那种写少读多、对一致性要求不高的场景,比如早年的一些报表系统。
3. MEMORY:数据全放内存里,速度快但MySQL重启数据就没了。一般拿来做临时表或者会话级缓存。

| 维度 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务 / 崩溃恢复 | 有（redo/undo） | 无 / 弱 |
| 锁 | 行锁 + 间隙等 | 表锁为主 |
| 外键 | 支持 | 不支持 |
| 索引组织 | **聚簇索引表** | 堆表 + 非聚簇 |
| 计数 | `count(*)` 需扫 | 易维护表级计数 |
| 适用 | OLTP 默认选择 | 历史只读、极少现代生产主库 |

**结论：** 现在答「默认 InnoDB」即可，MyISAM 作对比记忆。

**存储引擎怎么选**
99%的业务场景直接用InnoDB就完事了。MySQL5.5之后InnoDB就是默认引擎,官方也一直在优化它,全文索引、空间索引这些原来MyISAM有的能力,InnoDB现在也支持了。
只有几种特殊场景才考虑其他引擎:
1. 临时计算结果集,比如ETL中间表,可以用MEMORY引擎加速,但要注意数据易失性。
2. 日志归档、历史流水这种只写不改的数据,Archive引擎压缩率高,能省不少磁盘。
3. 搞MySQL Cluster分布式集群,才会用到 NDB。
MyISAM 基本可以淘汰了,MySQL 8.0已经把系统表从MyISAM迁移到InnoDB了,官方的态度很明确。

提问:InnoDB的行锁是怎么实现的?是锁住整行数据吗?
回答:InnoDB的行锁其实是锁索引记录,不是锁物理行。如果是SQL走的是主键索引,就锁主键索引上的那条记录;如果走的是二级索引,会先锁二级索引记录,再锁对应的主键记录。如果查询没走索引,那就退化成表锁了,因为要扫全表,所有记录都得锁。所以建索引不光是为了查询快,也是为了锁的粒度更细

提问:MyISAM既然只有表锁,为什么还说它读性能好?
回答:MyISAM 读性能好主要是因为它没有事务开销,不用维护urndo log,也不用做MVCC版本链查找。读的时候直接从B+树拿数据地址,去数据文件里顺序读就行。但这个优势是在无并发写或者写很少的前提下,一旦有写操作,表锁会把所有读都阻塞住,性能就崩了。

提问:MEMORY引擎数据放内存里,和Redis比有什么区别?3
回答:MEMORY引擎是MySQL进程内的内存存储,只能通过过SQL访问,数据结构固定是表,重启就丢。Redis是独立的KV存储服务,支持多种数据结构,有持久化机制,可以跨进科程访问。如果只是MySQL内部做临时表计算,MEMORY引擎够用;如果是分布式缓存、会话存储这种场景,用Redis,。两者定位完全不一样。

提问:生产环境怎么查看当前表用的是什么存储引擎?
回答:最直接的是SHOW TABLE STATUS LIKE 'table_name',Engine列就是引擎类型。也可以SHOW CREATE TABLE table_name 看建表语句最后的ENGINE参数。批量查的话用SELECT TABLE_NAME, ENGINE FROM information_schema.TABLES WHERE TABLE_SCHEMA=库名'。

### Q2. 从 MySQL 取数据是从磁盘读吗？Buffer Pool 做什么？

**优先内存。** InnoDB **Buffer Pool** 缓存数据页与索引页（默认 16KB/页）。

- 命中：内存读  
- 未命中：磁盘读入 BP，再返回  
- 修改：先改内存页（脏页），靠 redo 保证可恢复，后台刷盘  

**LRU 细节（加分）：** 年轻/老年子链表，降低全表扫描把热点页刷出去的污染。  
运维看：命中率、BP 大小（常设物理内存 50%~70%，视机器而定）。

### Q3. Change Buffer 是什么？作用？

Change Buffer是InnoDB存储引擎里的一块内存区域,专门用来来暂存对二级索引的变更操作。

当你执行INSERT、UPDATE、DELETE时,如果涉及的二级索引页不在Buffer Pool里,InnoDB不会立刻把索引页从磁盘加载进来,而是先把变更记录到ChangeBuffer中。

等后续这个索引页因为查询被读进内存,或者后台线程做Flush时,再把积攒的变更一次性合并进去。
这样做有两个好处:
1. 写入性能大幅提升。原本每次修改都要触发随机磁盘I/O把索引页读进来,现在直接写内存就返回了,省掉了大量随机
读。
2. 批量合并更高效。多次对同一个索引页的修改可以攒在一起,一次性应用,减少重复的磁盘读写次数。

**收益：** 写多、二级索引多时减少随机读。  
**限制：** 唯一索引通常要立即判断唯一性，不能像普通二级那样随意缓冲。

提问:Change Buffer和redolog有什么关系?它们不是都能提升写入性能吗?

回答:这俩解决的是不同层面的问题。redolog是把随机写变成顺顶序写,不管你改的是主键索引还是二级索引,都会写redo log,它解决的是"写数据页"的1/O问题。Change Buffer解决的是是"读索引页"的1/0问题,本来要先把索引页读进来才能改,现在不用读了,先记着。两者是配合关系,写ChangeBuuffer的时候也会写redolog来保证持久性。

提问:为什么唯一索引不能用ChangeBuffer?

回答:唯一索引在插入或更新时必须检查是否有重复值,这个检查必须读取索引页才能完成。既然无论如何都要把索引页读进内存,那把变更缓存起来就没意义了,反而多此一举。所以InnoDB干脆规定唯一索引不走Change Buffer。

提问:线上数据库要不要调大ChangeBuffer的比例?
回答:看场景。如果是写密集型业务、二级索引又多,可以考虑虑调大到30%-40%,让更多变更能攒起来批量合并。但调大意味着Buffer Pool里留给数据页和索引页的空间变少,可能影响查询的缓存命中率。最终还是得压测,看写入吞吐和查询响应时间的平衡点在哪。

### Q4. Doublewrite Buffer 是什么？作用？

问题：页大小 16KB，磁盘按 4KB 扇区写，掉电可能 **部分写（partial page write）** 毁掉页。

**双写：**

1. 先把脏页拷贝顺序写入 doublewrite 区域  
2. 再写回表空间各自页位置  

崩溃发现页校验失败，可用 doublewrite 中的副本来恢复。  
用一点额外写换页安全；生产勿随意关闭。

---

### Q5. Log Buffer 是什么？作用？

**redo log buffer：** 事务产生的 redo 先进入内存缓冲，再按 `innodb_flush_log_at_trx_commit` 等策略刷到 redo 文件。

作用：把「保证持久」变成对日志的顺序写，而不是每次提交都随机刷所有脏页。详见 [[06-日志与WAL]]。

---

### Q6. 一行记录是怎么存储的？

InnoDB 常见行格式 Dynamic/Compact：

- 变长字段长度列表、NULL 标志位  
- 记录头（含删除标记等）  
- **隐藏列：** `DB_TRX_ID`、`DB_ROLL_PTR`，（无用户主键时）`DB_ROW_ID`  
- 列值；过大列可能 **溢出到外部页**（off-page）  

页内用户记录按主键顺序组织，并有 Infimum / Supremum 伪记录界定范围。
