# Redis · 02-过期淘汰内存与BigKey

---

#### 9.Redis给缓存数据设置过期时间有什么用？
1. 减轻内存压力
2. 实现特殊功能, 比如发短信这些

#### 10.Redis是如何判断数据是否过期的？
Redis维护了一个过期字典来判断数据是否过期，可以理解为一个Map存储到key也还是对应数据的key，value是一个long long类型的uninx时间戳，在访问数据的时候会判断时间戳对应时间是否过期的
#### 11.Redis过期数据的删除策略（数据过期策略）了解吗？
删除策略主要分为两种
1. 定期删除，也就是按照SLOW或者FAST的频率设置定期的抽取一部分数据判断其是否过期，并且将其删除
2. 惰性删除，也就是在访问这个数据的时候才判断其是否过期，如果过期再将其删除
还有衍生删除策略：主动删除和定时删除，定时删除就是给key设置了过期时间然后到时间就删除

#### 12.Redis的内存淘汰机制了解吗？{假如缓存过多，内存是有限的，内存}
**1.volatile-lru（least recently used）：从已设置过期时间的数据集（server.db[i].expires）中挑选最近最少使用的数据淘汰。**
**2.volatile-ttl：从已设置过期时间的数据集（server.db[i].expires）中挑选将要过期的数据淘汰。**
**3.volatile-random：从已设置过期时间的数据集（server.db[i].expires）中任意选择数据淘汰。**
**4.allkeys-lru（least recently used）：当内存不足以容纳新写入数据时，在键空间中，移除最近最少使用的 key（这个是最常用的）。**
**5.allkeys-random：从数据集（server.db[i].dict）（全体key）中任意选择数据淘汰。**
**6.no-eviction：禁止驱逐数据，也就是说当内存不足以容纳新写入数据时，新写入操作会报错。这个应该没人使用吧！**
**7.allkeys-lfu: 对全体key，基于LFU算法进行淘汰。**
**8.volatile-lfu:对设置了TTL的key，基于LFU算法进行淘汰**

#### 13.如何解决大量key集中过期的问题？
| 方案                         | 实现层面      | 优点         | 适用场景           |
| -------------------------- | --------- | ---------- | -------------- |
| TTL 随机偏移                   | 写入业务      | 零成本、简单     | 通用常规缓存         |
| hz/active-expire-effort 调参 | Redis 服务端 | 无需改代码      | 存量业务快速缓解       |
| lazyfree 异步删除              | Redis 配置  | 解决大 key 阻塞 | 包含集合、大字符串缓存    |
| Redis 集群分槽 / 多实例           | 部署架构      | 压力节点隔离     | 海量 key 业务      |
| ZSET 自定义过期清理               | 业务代码      | 完全可控、无雪崩   | 活动批量缓存、百万级 key |
| 分批次预热错峰                    | 业务预热      | 从源头减少集中过期  | 营销、秒杀活动        |
| 本地二级缓存                     | 应用层       | 兜底防 DB 雪崩  | 高并发核心接口        |

#### 14.什么是Bigkey？
一个key对应的Value比较大就一般称呼这个key为bigKey，比如在String类型中，如果对应的value超过了1MB一般就会被称作BigKey


#### 15.Bigkey是怎么产生的？有什么危害？
一般Bigkey的产生主要是因为
1. 对业务的规模预估不当
2. 程序设计不当, 比如选择了不适合的数据结构
3. Hash这种类型没有清理无用的空数据

危害:
1. BigKey会阻塞工作线程的操作造成卡顿
2. BigKey会占据大量的空间，甚至会导致OOM
3. **客户端超时阻塞**：由于 Redis 执行命令是单线程处理，然后在操作大 key 时会比较耗时，那么就会阻塞 Redis，从客户端这一视角看，就是很久很久都没有响应。
4. **网络阻塞**：每次获取大 key 产生的网络流量较大，如果一个 key 的大小是 1 MB，每秒访问量为 1000，那么每秒会产生 1000MB 的流量，这对于普通千兆网卡的服务器来说是灾难性的。
5. 大 key 造成的阻塞问题还会进一步影响到主从同步和集群扩容。
6. Bigkey可能会导致内存分布不均，这也会因此直接影响到查询效率

#### 16.如何发现Bigkey？
1. 通过--bigkeys参数发现bigkey
2. 通过Scan命令去扫描
3. 通过公有云服务去判断
4. 通过开源技术去扫描RDB文件

#### 17.如何处理Bigkey？
1. 分割BigKey，将BigKey分为多个小key
2. 选择合适的数据结构，比如适合用Hash的就用哈希，不是全部都是用String转json去存这种
3. 进行lazy-free定期惰性删除处理
4. 优化存储策略，采用冷热数据分离的法子，对于不常用的数据就不放在Redis里面
5. 使用压缩数据的方式减少占据的Value量
6. 使用集群的方式将拆分的Key进行存储来优化
