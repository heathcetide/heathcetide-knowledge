# 17 · 反射与泛型

> 反射吃性能、泛型补类型安全——知道边界比背 API 重要。

---

## 面试题

### Q1. 反射能做什么？性能如何？

`reflect` 在运行时检查类型、读写值、调方法，支撑：

- 序列化（encoding/json）  
- 依赖注入 / ORM 映射  
- 通用库  

代价：

- 比静态代码**慢**（装箱、接口、名字查找）  
- 易 runtime panic，编译期难查  
- 代码可读性差  

原则：**库可以反，业务热点少反**；能泛型/代码生成就别反射。

---

### Q2. `Type` 和 `Value` 区别？

- `reflect.TypeOf(x)` → 类型信息  
- `reflect.ValueOf(x)` → 值的运行时表示  

可设性：`CanSet()`；改字段常需导出字段 + `Elem()` 解指针。  
`Interface()` 把 Value 变回 `interface{}`。

---

### Q3. 反射修改结构体字段的条件？

1. 传入指针：`reflect.ValueOf(&s).Elem()`  
2. 字段**导出**（大写）  
3. `CanSet()` 为 true  

未导出字段可以看（同包外仍受限），一般不能乱改。

---

### Q4. Go 泛型解决什么问题？

Go 1.18+ 类型参数：在保持类型安全下写通用数据结构/算法，减少 `interface{}` + 断言。

```go
func Map[T, U any](in []T, f func(T) U) []U {
    out := make([]U, len(in))
    for i, v := range in {
        out[i] = f(v)
    }
    return out
}
```

约束：`any`、`comparable`、自定义 interface 约束。

---

### Q5. 泛型有哪些限制？（常考点）

口述几条即可：

- 方法不能再额外带自己的类型参数（类型参数在类型/函数定义处）  
- 不能对类型参数随意用所有操作，受约束限制  
- 特化/单态化由编译器处理，极端情况注意代码体积  
- 反射与泛型是不同机制，别混为一谈  

---

### Q6. `any`、`interface{}`、`comparable`？

- `any` ≡ `interface{}` 别名  
- `comparable`：可用于 `==`/`!=` 的类型（map key 约束等）  
- 自定义约束：`interface{ ~int | ~string; String() string }` 等  

---

### Q7. 什么时候用泛型，什么时候用接口？

| | 接口 | 泛型 |
| --- | --- | --- |
| 行为多态、多种实现 | 合适 | 未必需要 |
| 容器/算法要保留具体类型 | 弱（要断言） | **合适** |
| 已有接口生态（io.Reader） | 继续用 | 不必强行改 |

口诀：**要行为用接口，要类型参数化数据结构用泛型。**

---

### Q8. 类型断言、类型开关、反射如何分工？

1. 已知少数类型 → 断言 / `switch x.(type)`  
2. 库要处理任意类型 → 反射或泛型 + 约束  
3. 性能敏感路径 → 避免反射，可代码生成  

接口底层见 [[06-接口与类型断言]]。
