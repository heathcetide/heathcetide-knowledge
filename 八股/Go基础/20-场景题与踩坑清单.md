## 面试题

### Q1. 实现一个带超时的任务执行函数？

要点：Context 超时 + 结果 channel + select；防止泄漏。

```go
func RunWithTimeout(ctx context.Context, d time.Duration, fn func(context.Context) error) error {
    ctx, cancel := context.WithTimeout(ctx, d)
    defer cancel()
    errc := make(chan error, 1)
    go func() { errc <- fn(ctx) }()
    select {
    case <-ctx.Done():
        return ctx.Err()
    case err := <-errc:
        return err
    }
}
```

追问：`fn` 不认 ctx 怎么办？→ 只能超时返回，goroutine 仍可能继续，要约定可取消或隔离进程。

### Q2. 限流：每秒最多 N 个请求怎么做？

思路任选其一口述：

1. 缓冲 channel 信号量 + 时间窗口补充令牌  
2. `golang.org/x/time/rate` 令牌桶  
3. 漏桶 / 滑动窗口（分布式再用 Redis）  

本地进程内：令牌桶最常答。

3. 热点提前刷新 / 逻辑过期  
4. 空值短缓存防穿透

### Q4. 这段代码为什么死锁？（经典）

```go
ch := make(chan int)
ch <- 1          // 无缓冲，无接收方 → 卡住
<-ch
```

或：

```go
var mu sync.Mutex
mu.Lock()
mu.Lock() // Mutex 不可重入 → 死锁
```

或：持锁时向无缓冲 channel 发送，对端也要同锁 → 循环等待。

### Q5. 为什么 `waitgroup` 用法会 panic / 卡住？

```go
// 错：Add 在子 goroutine 里且与 Wait 竞态
go func() {
    wg.Add(1) // 可能 Wait 已经开始
    defer wg.Done()
}()
wg.Wait()
```

正确：`Add` 在 `go` 之前；计数匹配。见 [[16-sync包与原子操作]]。

### Q6. 打印发现接口 `== nil` 判断失效？

返回了 `nil` 指针但装进了 `error`/`interface{}`。见 [[06-接口与类型断言#Q3]]。  
修复：`return nil` 而不是 `return err`（当 err 是 typed nil）。

### Q7. 切片传给函数 append 后外面没变？

函数里的 slice 头是拷贝；`append` 换底层后只改了副本头。  
要：返回新 slice，或传 `*[]T`。见 [[03-数组与切片#Q5]]。

### Q8. 如何设计「可取消的 worker 池」口述稿？

1. 任务 channel + N worker  
2. root `Context` 取消  
3. 每个 worker `select` job / `ctx.Done()`  
4. 生产者结束后 `close(jobs)`  
5. `WaitGroup` 等待 worker，再关 results  
6. `Shutdown` 调 cancel + 超时等待  

串联 [[11-Goroutine与Channel]] [[12-Select与并发模式]] [[15-Context]]。

### Q9. Go 内存高，如何一步步查？

1. 看是否 goroutine 泄漏（数量、profile）  
2. heap profile：谁分配、谁残留  
3. 大 map/缓存有无上限  
4. 切片引用大底层（[[03-数组与切片#Q14]]）  
5. `GOMEMLIMIT` / 容器 limit 是否合理  
6. 复用与 `sync.Pool` 是否用对  

见 [[14-GC与内存逃逸]]、[[19-工程实践与性能排查]]。

### Q12. 「协程饥饿」现场怎么答？

先分层，再举例（完整展开见各专章）：

1. **调度层：** 旧协作式紧循环饿死同核 G → 现靠异步抢占；仍可能 CPU 打满导致延迟差 → [[13-GMP调度器#Q6b]]  
2. **channel/select：** 缓冲区长期满/空、`default` 空转、某 case 总就绪挤掉其它 → [[11-Goroutine与Channel#Q14]] [[12-Select与并发模式#Q10]]  
3. **锁层：** RWMutex 写者被读者续杯饿死（Go 用「写者等待则阻新读者」缓解）；`RLock` 直接 `Lock` 升级死锁 → [[16-sync包与原子操作#Q1b]] [[16-sync包与原子操作#Q1c]]  

别把「堵在锁/channel 上」笼统说成「调度器不公平」。
