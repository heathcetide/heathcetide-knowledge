# 08 · SQL 语法与调优（详解）

调优题按 **「先计划、再 SQL、再结构、再架构」** 答，避免只说「加索引」。

---

## 面试题

### Q1. count(*)、count(1)、count(字段) 区别？

- InnoDB **没有**像 MyISAM 那样一直维护精确总行数；`count(*)` 通常要扫索引（优化器会选较小二级索引）累加  
- `count(*)` 与 `count(1)` 语义都是计行，优化后可等同，不必纠结谁更快  
- `count(列)`：**不统计该列为 NULL 的行**  

有覆盖索引、只计部分条件时，尽量让 count 走窄索引。

---

### Q2. INNER / LEFT / RIGHT JOIN？为何不推荐过多表 JOIN？

- **INNER：** 仅保留匹配行  
- **LEFT：** 保留左表全部，右表无匹配则 NULL  
- **RIGHT：** 对称；可改写成 LEFT，团队常统一用 LEFT  

**多表 JOIN 问题：** 优化器空间大、中间结果膨胀、执行计划不稳、难分库、锁与缓存失效面大。  
实战：控制 JOIN 数量；热点查询冗余字段；复杂报表走数仓/ES。

---

### Q3. DELETE、DROP、TRUNCATE 区别？

| | DELETE | TRUNCATE | DROP |
| --- | --- | --- | --- |
| 粒度 | 按行（可带 WHERE） | 整表清空 | 删表 |
| 事务 | InnoDB 可回滚 | DDL 味，通常隐式提交 | DDL |
| 触发器 | 可逐行触发 | 不触发 | — |
| 自增 | 一般保留当前值 | 重置 | — |
| 速度 | 大表慢（写 undo/redo） | 通常更快 | — |

---

### Q4. LIMIT 大偏移为何慢？深度分页 / 游标分页？

`LIMIT 1000000, 10` 仍需定位到第 1000001 行，成本随偏移涨。  
`LIMIT 10` 只取前 10，轻。

**游标（seek）分页：**

```sql
SELECT * FROM t WHERE id > #{lastId} ORDER BY id LIMIT 10;
```

优势：走索引范围，不做巨大 OFFSET。适合「下一页」；随机跳页仍难，可业务限制深翻页。

**延迟关联：** 子查询先查出主键再回表取列，减少回表宽度。

---

### Q5. EXISTS vs IN？

现代优化器常互相改写。传统经验：相关子查询用 EXISTS；子查询结果集小而明确用 IN。  
`NOT IN` 遇 NULL 结果恒未知（踩坑）；优先 `NOT EXISTS` 或防 NULL。

---

### Q6. 如何做 SQL 调优？性能优化方法？慢 SQL 监控？谈优化经验？

**经验分层：**

1. **监控发现：** 慢日志、`performance_schema`、APM  
2. **计划确认：** EXPLAIN ANALYZE，盯 type/rows/Extra  
3. **改写与索引：** 覆盖、最左、避免失效、深分页、拆大 SQL  
4. **表与数据：** 归档、分区、冷热、类型  
5. **实例与架构：** BP、读写分离、缓存、分库分表  

上线卡控：核心 SQL 必须带计划评审。
