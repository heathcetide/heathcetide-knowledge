**2 Spring 事务的传播行为**
<font style="color:rgb(82, 196, 26);">REQUIRED</font>:如果当前上下文中存在事务，那么加入该事务，如果不存在事务，创建一个事务，这是默认的传播属性值；
<font style="color:rgb(82, 196, 26);">REQUIRES_NEW:</font>每次都会新建一个事务，并且同时将上下文中的事务挂起，执行当前新建事务完成以后，上下文事务恢复再执行；
<font style="color:rgb(82, 196, 26);">SUPPORTS</font>：如果当前上下文存在事务，则支持事务加入事务，如果不存在事务，则使用非事务的方式执行；
<font style="color:rgb(82, 196, 26);">NOT_SUPPORTED:</font>如果当前上下文中存在事务，则挂起当前事务，然后新的方法在没有事务的环境中执行；
<font style="color:rgb(82, 196, 26);">NESTED</font>:如果当前上下文中存在事务，则嵌套事务执行，如果不存在事务，则新建事务；
<font style="color:rgb(82, 196, 26);">NEVER:</font>如果当前上下文中存在事务，则抛出异常，否则在无事务环境上执行代码.


**4 Spring事务使用注意的点长事务**
**4.1 长事务的典型场景**
这是一个经典的场景,在很多场景都会用到，这个业务场景是，通过http请求工作流测接口， 然后保存本地的报销单，然后在这个方法上加上@Transactional事务注解。
<font style="color:rgb(114, 46, 209);">会存在长事务的问题。也就是运行时间比较长，长时间未提交的事务，也可以称之为大事务。</font>
**4.2 长事务分析**
Spring 遇到该注解时(@Transactional事务注解)，会自动从数据库连接池中获取 connection，并开启事务然后绑定到 ThreadLocal 上，对于@Transactional注解包裹的整个方法都是使用同一个connection连接。如果我们出现了耗时的操作，<font style="color:rgb(232, 50, 60);">比如第三方接口调用，业务逻辑复杂，大批量数据处理等就会导致我们我们占用这个connection的时间会很长，数据库连接一直被占用不释放</font>。一旦类似操作过多，就会导致数据库连接池耗尽；
在一个事务中执行RPC操作导致数据库连接池撑爆属于是典型的长事务问题，类似的操作还有在事务中进行大量数据查询，业务规则处理等。

**4.3 危害**
<font style="color:rgb(114, 46, 209);">对于上述场景下的，流量稍微高一点的业务接口，那么这种场景下的长事务就是灾难性的了</font>

```plain
public class TestApplicationContextInitializer implements ApplicationContextInitializer {

}
```

**3.4)InstantiationAwareBeanPostProcessor**
<font style="color:rgb(0, 0, 0);">org.springframework.beans.factory.config.InstantiationAwareBeanPostProcessor</font>
<font style="color:rgb(0, 0, 0);">该接口继承了</font><font style="color:rgb(30, 107, 184);">BeanPostProcess</font><font style="color:rgb(0, 0, 0);">接口；</font>
<font style="color:rgb(0, 0, 0);">该接口与</font><font style="color:rgb(30, 107, 184);">BeanPostProcess</font>接口的区别
 1 <font style="color:rgb(114, 46, 209);">BeanPostProcess</font>接口只在bean的初始化阶段进行扩展（注入spring上下文前后), <font style="color:rgb(114, 46, 209);">InstantiationAwareBeanPostProcessor</font>接口在此基础上增加了3个方法，把可扩展的范围增加了实例化阶段和属性注入阶段。
**顺序**
<font style="color:rgb(0, 0, 0);">该类主要的扩展点有以下5个方法，主要在bean生命周期的</font><font style="color:rgb(114, 46, 209);">两大阶段:实例化阶段和初始化阶段</font>
<font style="color:rgb(30, 107, 184);">postProcessBeforeInstantiation，</font><font style="color:rgb(1, 1, 1);">实例化bean之前，相当于new这个bean之前</font>
<font style="color:rgb(30, 107, 184);">postProcessAfterInstantiation，</font><font style="color:rgb(1, 1, 1);">实例化bean之后，相当于new这个bean之后</font>
<font style="color:rgb(30, 107, 184);">postProcessPropertyValues，</font><font style="color:rgb(1, 1, 1);">bean已经实例化完成，在属性注入时阶段触发，</font><font style="color:rgb(30, 107, 184);">@Autowired</font><font style="color:rgb(1, 1, 1);">,</font><font style="color:rgb(30, 107, 184);">@Resource</font><font style="color:rgb(1, 1, 1);">等注解原理基于此方法实现</font>
<font style="color:rgb(30, 107, 184);">postProcessBeforeInitialization，</font><font style="color:rgb(1, 1, 1);">初始化bean之前，相当于把bean注入spring上下文之前</font>
<font style="color:rgb(30, 107, 184);">postProcessAfterInitialization，</font><font style="color:rgb(1, 1, 1);">初始化bean之后，相当于把bean注入spring上下文之后</font>
**<font style="color:rgb(1, 1, 1);">场景</font>**
<font style="color:rgb(0, 0, 0);">使用场景：这个扩展点非常有用 ，无论是写中间件和业务中，都能利用这个特性。比如对实现了某一类接口的bean在各个生命期间进行收集，或者对某个类型的bean进行统一的设值等等。</font>
**<font style="color:rgb(0, 0, 0);">拓展方式</font>**


```plain
public class TestInstantiationAwareBeanPostProcessor implements InstantiationAwareBeanPostProcessor {

 @Override
 public Object postProcessBeforeInitialization(Object bean, String beanName) throws BeansException {
 System.out.println("[TestInstantiationAwareBeanPostProcessor] before initialization " + beanName);
 return bean;
 }

 @Override
 public Object postProcessAfterInitialization(Object bean, String beanName) throws BeansException {
 System.out.println("[TestInstantiationAwareBeanPostProcessor] after initialization " + beanName);
 return bean;
 }

 @Override
 public Object postProcessBeforeInstantiation(Class<?> beanClass, String beanName) throws BeansException {
 System.out.println("[TestInstantiationAwareBeanPostProcessor] before instantiation " + beanName);
 return null;
 }

 @Override
 public boolean postProcessAfterInstantiation(Object bean, String beanName) throws BeansException {
 System.out.println("[TestInstantiationAwareBeanPostProcessor] after instantiation " + beanName);
 return true;
 }

 @Override
 public PropertyValues postProcessPropertyValues(PropertyValues pvs, PropertyDescriptor[] pds, Object bean, String beanName) throws BeansException {
 System.out.println("[TestInstantiationAwareBeanPostProcessor] postProcessPropertyValues " + beanName);
 return pvs;
 }
```

### 3.6)@PostConstruct

### 3.8)FactoryBean
org.springframework.beans.factory.FactoryBean

#### 顺序及说明
<font style="color:rgb(0, 0, 0);">一般情况下，Spring通过反射机制利用bean的class属性指定支线类去实例化bean，在某些情况下，实例化Bean过程比较复杂，如果按照传统的方式，则需要在bean中提供大量的配置信息。配置方式的灵活性是受限的，这时采用编码的方式可能会得到一个简单的方案。Spring为此提供了一个</font><font style="color:rgb(30, 107, 184);">org.springframework.bean.factory.FactoryBean</font><font style="color:rgb(0, 0, 0);">的工厂类接口，用户可以通过实现该接口定制实例化Bean的逻辑。</font><font style="color:rgb(30, 107, 184);">FactoryBean</font><font style="color:rgb(0, 0, 0);">接口对于Spring框架来说占用重要的地位，Spring自身就提供了70多个</font><font style="color:rgb(30, 107, 184);">FactoryBean</font><font style="color:rgb(0, 0, 0);">的实现。它们隐藏了实例化一些复杂bean的细节，给上层应用带来了便利。从Spring3.0开始，</font><font style="color:rgb(30, 107, 184);">FactoryBean</font><font style="color:rgb(0, 0, 0);">开始支持泛型，即接口声明改为</font><font style="color:rgb(30, 107, 184);">FactoryBean<T></font><font style="color:rgb(0, 0, 0);">的形式。</font>

#### <font style="color:rgb(0, 0, 0);">场景</font>
<font style="color:rgb(0, 0, 0);">使用场景：用户可以扩展这个类，来为要实例化的bean作一个代理，比如为该对象的所有的方法作一个拦截，在调用前后输出一行log，模仿</font><font style="color:rgb(30, 107, 184);">ProxyFactoryBean</font><font style="color:rgb(0, 0, 0);">的功能。</font>

#### <font style="color:rgb(0, 0, 0);">拓展方式</font>

```plain
public class TestFactoryBean implements FactoryBean<TestFactoryBean.TestFactoryInnerBean> {

 @Override

 }

 @Override
 public boolean isSingleton() {
 return true;
 }

 public static class TestFactoryInnerBean{

 }
}
```

# 1 Spring事务不生效
**1 代码层面Spring事务不生效的场景**
**1.1）访问权限**
java的访问权限主要有四种：private、default、protected、public，它们的权限从左到右，依次变大。

```plain
@Service
public class UserService {

 @Transactional
 private void add(UserModel userModel) {
 saveData(userModel);
 updateData(userModel);
 }
}
```

我们可以看到add方法的访问权限被定义成了private，这样会导致事务失效，spring要求被代理方法必须是public的。


#### 1.2）方法用final修饰
```plain
@Service
public class UserService {
 @Transactional
 public final void add(UserModel userModel){
 saveData(userModel);
 updateData(userModel);
 }
}
```

我们可以看到add方法被定义成了final的，这样会导致事务失效;

**为什么?**

<font style="color:rgb(38, 38, 38);">spring事务的源码，可能会知道spring事务底层使用了aop，也就是通过jdk动态代理或者cglib，帮我们生成了代理类，在代理类中实现的事务功能;</font>

<font style="color:rgb(38, 38, 38);">但如果某个方法用final修饰了，那么在它的代理类中，就无法重写该方法，而添加事务功能.</font>

<font style="color:rgb(89, 89, 89);background-color:rgb(251, 249, 253);"></font>

<font style="color:rgb(89, 89, 89);background-color:rgb(251, 249, 253);">注意：如果某个方法是static的，同样无法通过动态代理，变成事务方法。</font>

#### <font style="color:rgb(38, 38, 38);">1.3)方法内部调用</font>
```plain
@Service
public class UserService {

 @Autowired
 private UserMapper userMapper;


 public void add(UserModel userModel) {
 userMapper.insertUser(userModel);
 updateStatus(userModel);
 }

 @Transactional
 public void updateStatus(UserModel userModel) {
 doSameThing();
 }
}
0
```

add方法调用事务方法updateStatus，这个方法通过this调用dodoSameThing(),会导致事务不起作用。

**为什么？**

<font style="color:#E8323C;">这种拆分会命中使用@Transactional注解时事务不生效的经典场景，很多新手非常容易犯这个错误，@Transactional注解的声明式事务是通过spring aop起作用的，而spring aop需要生成代理对象，直接在同一个类中方法调用使用的还是原始对象，事务不生效；</font>

updateStatus方法拥有事务的能力是因为spring aop生成代理了对象，但是这种方法直接调用了this对象的方法，所以updateStatus方法不会生成事务。


<font style="color:rgb(89, 89, 89);background-color:rgb(251, 249, 253);">注意：如果有些场景，确实想在同一个类中的某个方法中，调用它的另一个方法，该怎么办？</font>

#### <font style="color:rgb(38, 38, 38);">1.4)多线程调用</font>
<font style="color:rgb(38, 38, 38);">在实际项目开发中，多线程的使用场景还是挺多的。如果spring事务用在多线程场景中，会有问题吗？</font>

```plain
@Slf4j
@Service
public class UserService {

 @Autowired
 private UserMapper userMapper;
 @Autowired
 private RoleService roleService;

 @Transactional
 public void add(UserModel userModel) throws Exception {
 userMapper.insertUser(userModel);
 new Thread(() -> {
 roleService.doOtherThing();
 }).start();
 }
}

@Service
public class RoleService {
 @Transactional
 public void doOtherThing() {
 System.out.println("保存role表数据");
 }
}
```

在事务方法add中开启一个线程，去执行RoleService的事务方法，这样事务会生效吗？

**为什么？**

<font style="color:rgb(38, 38, 38);">这样会导致</font><font style="color:#E8323C;">两个方法不在同一个线程中，获取到的数据库连接不一样，从而是两个不同的事务</font><font style="color:rgb(38, 38, 38);">。如果想doOtherThing方法中抛了异常，add方法也回滚是不可能的。</font>

<font style="color:rgb(38, 38, 38);">我们说的同一个事务，其实是指同一个数据库连接，只有拥有同一个数据库连接才能同时提交和回滚。如果在不同的线程，拿到的数据库连接肯定是不一样的，所以是不同的事务。</font>

<font style="color:rgb(38, 38, 38);"></font>

#### <font style="color:rgb(38, 38, 38);">1.5)异常没有抛出</font>
<font style="color:rgb(38, 38, 38);">事务不会回滚，最常见的问题是：开发者在代码中手动try...catch了异常。</font>

```plain
@Slf4j
@Service
public class UserService {

 @Transactional
 public void add(UserModel userModel) {
 try {
 saveData(userModel);
 updateData(userModel);
 } catch (Exception e) {
 log.error(e.getMessage(), e);
 }
 }
}
```

如果想要spring事务能够正常回滚，必须抛出它能够处理的异常。如果没有抛异常，则spring认为程序是正常的。


#### 1.6)手动抛了别的异常
开发者在捕获异常，但如果抛的异常不正确，spring事务也不会回滚;

```plain
@Slf4j
@Service
public class UserService {

 @Transactional
 public void add(UserModel userModel) throws Exception {
 try {
 saveData(userModel);
 updateData(userModel);
 } catch (Exception e) {
 log.error(e.getMessage(), e);
 throw new Exception(e);
 }
 }
}
```

在catch里面抛出了Exception的异常，因为spring事务，默认情况下只会回滚RuntimeException(运行时异常)，

对于普通的Exception（非运行时异常），它不会回滚。


#### 1.7）自定义了回滚异常
在使用@Transactional注解声明事务时，有时我们想自定义回滚的异常，可以通过设置rollbackFor参数，来完成这个功能。

<font style="color:#E8323C;">但如果这个参数的值设置错了，就会引出一些莫名其妙的问题</font>，例如
```plain
@Slf4j
@Service
public class UserService {

 @Transactional(rollbackFor = BusinessException.class)
 public void add(UserModel userModel) throws Exception {
 saveData(userModel);
 updateData(userModel);
 }
}
```

程序报错了，抛了SqlException、DuplicateKeyException等异常。而BusinessException是我们自定义的异常，报错的异常不属于BusinessException，所以事务也不会回滚。


**阿里巴巴规范：**

<font style="color:rgb(74, 74, 74);">即使rollbackFor有默认值，但阿里巴巴开发者规范中，还是要求开发者重新指定该参数。</font>

<font style="color:rgb(74, 74, 74);">因为如果使用默认值，一旦程序抛出了Exception，事务不会回滚，这会出现很大的bug。所以，建议一般情况下，将该参数设置成：Exception或Throwable。</font>

<font style="color:rgb(74, 74, 74);"></font>

<font style="color:rgb(74, 74, 74);"></font>

#### <font style="color:rgb(74, 74, 74);">1.8)嵌套事务回滚多了</font>
```plain
public class UserService {
 @Autowired
 private UserMapper userMapper;

 @Autowired
 private RoleService roleService;

 @Transactional
 public void add(UserModel userModel) throws Exception {
 userMapper.insertUser(userModel);
 roleService.doOtherThing();
 }
}


@Service
public class RoleService {
 @Transactional(propagation = Propagation.NESTED)
 public void doOtherThing() {
 System.out.println("保存role表数据");
 }
}
```

**<font style="color:rgb(74, 74, 74);">描述：</font>**

<font style="color:rgb(38, 38, 38);">UserService里的事务方法add，add方法采用默认的事务传播行为，调用RoleService的doOtherThing方法，并且这个方法的传播行为是</font><font style="color:#EB2F96;">Propagation.NESTED，</font>

**要实现的效果：**

<font style="color:rgb(38, 38, 38);">UserService里的事务方法add方法中的userMapper.insertUser()的执行， 不受RoleService类中的doOtherThing（）事务方法的影响；</font>

<font style="color:rgb(38, 38, 38);">结果：</font><font style="color:rgb(74, 74, 74);">insertUser也回滚了</font>

**<font style="color:rgb(74, 74, 74);">为什么：</font>**

<font style="color:rgb(74, 74, 74);">因为doOtherThing方法出现了异常，会继续往上抛，这种情况是直接回滚了整个事务。</font>

**<font style="color:rgb(74, 74, 74);">解决：</font>**

<font style="color:rgb(74, 74, 74);">可以将内部嵌套事务放在try/catch中，并且不继续往上抛异常，这样就能保证，如果内部嵌套事务中出现异常，只回滚内部事务，而不影响外部事务。</font>

<font style="color:rgb(74, 74, 74);"></font>

<font style="color:rgb(74, 74, 74);">#将</font><font style="color:rgb(38, 38, 38);"> roleService.doOtherThing()放入到catch里面,这样 userMapper.insertUser(userModel)方法的事务，不受其影响。</font>

```plain
@Slf4j
@Service
public class UserService {

 @Autowired
 private UserMapper userMapper;

 @Autowired
 private RoleService roleService;

 @Transactional
 public void add(UserModel userModel) throws Exception {
 userMapper.insertUser(userModel);
 try {
 roleService.doOtherThing();
 } catch (Exception e) {
 log.error(e.getMessage(), e);
 }
 }
}
```

<font style="color:rgb(38, 38, 38);">
</font>**<font style="color:rgb(38, 38, 38);">2 事务的传播特性导致事务不回滚</font>**<font style="color:rgb(38, 38, 38);">
</font>**<font style="color:rgb(38, 38, 38);">2.1)错误的传播特性</font>**<font style="color:rgb(38, 38, 38);">
</font><font style="color:rgb(38, 38, 38);">我们在使用@Transactional注解时，是可以指定propagation参数的,该参数的作用是指定事务的传播特性。
</font><font style="color:rgb(82, 196, 26);">REQUIRED</font><font style="color:rgb(38, 38, 38);"> 如果当前上下文中存在事务，那么加入该事务，如果不存在事务，创建一个事务，这是默认的传播属性值；
</font><font style="color:rgb(82, 196, 26);">REQUIRES_NEW </font><font style="color:rgb(38, 38, 38);">每次都会新建一个事务，并且同时将上下文中的事务挂起，执行当前新建事务完成以后，上下文事务恢复再执行；
</font><font style="color:rgb(82, 196, 26);">SUPPORTS</font><font style="color:rgb(38, 38, 38);"> 如果当前上下文存在事务，则支持事务加入事务，如果不存在事务，则使用非事务的方式执行；
</font><font style="color:rgb(82, 196, 26);">NOT_SUPPORTED </font><font style="color:rgb(38, 38, 38);">如果当前上下文中存在事务，则挂起当前事务，然后新的方法在没有事务的环境中执行；
</font><font style="color:rgb(82, 196, 26);">NESTED</font><font style="color:rgb(38, 38, 38);"> 如果当前上下文中存在事务，则嵌套事务执行，如果不存在事务，则新建事务；
</font><font style="color:rgb(82, 196, 26);">NEVER </font><font style="color:rgb(38, 38, 38);">如果当前上下文中存在事务，则抛出异常，否则在无事务环境上执行代码。


</font>

```plain
@Service
public class UserService {

 @Transactional(propagation = Propagation.NEVER)
 public void add(UserModel userModel) {
 saveData(userModel);
 updateData(userModel);
 }
}
```

add方法的事务传播特性定义成了Propagation.NEVER，这种类型的传播特性不支持事务，如果有事务则会抛异常。


<font style="color:rgb(89, 89, 89);background-color:rgb(251, 249, 253);">注意：目前只有三种事务的传播特性才会创建新的事物:REQUIRED、REQUIRES_NEW、NEVER</font>

### <font style="color:rgb(89, 89, 89);background-color:rgb(251, 249, 253);">3 大事物</font>
 在使用spring事务时，有个让人非常头疼的问题，就是大事务问题 ；

```plain
@Service
public class UserService {

 @Autowired
 private RoleService roleService;

 @Transactional
 public void add(UserModel userModel) throws Exception {
 query1();
 query2();
 query3();
 roleService.save(userModel);
 update(userModel);
 }
}


@Service
public class RoleService {
 @Autowired
 private RoleService roleService;

 @Transactional
 public void save(UserModel userModel) throws Exception {
 query4();
 query5();
 query6();
 saveData(userModel);
 }
}

```

**3.1)描述：**
UserService方法中需要事务的只有两行代码
<font style="color:rgb(235, 47, 150);">roleService.save(userModel);</font>
<font style="color:rgb(235, 47, 150);">update(userModel);</font>
在RoleService类中，只有这一行需要事务
<font style="color:rgb(235, 47, 150);">saveData(userModel);</font>
<font style="color:rgb(235, 47, 150);">这些方法最终都在</font>UserService的add方法里，这里面还有很多查询的方法也被加在同一个事务中，当query方法比较多，调用层级比较深的情况下，会造成整个事务非常耗时，从而造成大事务问题。
**3.2)解决大失误**
** Spring事务的实现方式**
1,以@Transactional注解形式实现的申明式事务;
 2,通过手动编写代码实现的事务,也叫编程式事务;
 在spring中为了支持编程式事务，专门提供了一个类：TransactionTemplate，在它的execute方法中，就实 现了事务的功能;
 #TransactionTemplate实现编程式事务，在这个例子中，事务只有addData1和updateData2两个方法在事务 里。避免了查询对整个程序性能的影响,能更小粒度控制事务。


<font style="color:rgb(38, 38, 38);background-color:rgb(245, 245, 245);">
</font>

```plain
 @Autowired
 private TransactionTemplate transactionTemplate;

 ...

 public void save(final User user) {
 queryData1();
 queryData2();
 transactionTemplate.execute((status) => {
 addData1();
 updateData2();
 return Boolean.TRUE;
 })
 }
```

#### 3.3)使用Spring事务的一些小建议
 建议在项目中少使用@Transactional注解开启事务，少用申明式事务;

 如果项目中有些业务逻辑比较简单，而且不经常变动，使用@Transactional注解开启事务开启事务也无妨， 因为它更简单，开发效率更高，但是千万要小心事务失效的问题.

# 2 Spring事务中需要注意长事务
**1 长事务代码**


<font style="color:rgb(38, 38, 38);background-color:rgb(245, 245, 245);">
</font>

```plain
 /**
 * 保存报销单并创建工作流
 */
@Transactional(rollbackFor = Exception.class)
public void save(RequestBillDTO requestBillDTO){
 //调用流程HTTP接口创建工作流
 workflowUtil.createFlow("BILL",requestBillDTO);

 //转换DTO对象
 RequestBill requestBill = JkMappingUtils.convert(requestBillDTO, RequestBill.class);
 requestBillDao.save(requestBill);
 //保存明细表
 requestDetailDao.save(requestBill.getDetail())
}
```

**描述：**

这是一个经典的场景,在很多场景都会用到，这个业务场景是，通过http请求工作流测接口， 然后保存本地的报销单，然后在这个方法上加上@Transactional事务注解。

**问题：**

会存在长事务的问题。也就是运行时间比较长，长时间未提交的事务，也可以称之为大事务。

**分析：**

Spring 遇到该注解时(@Transactional事务注解)，会自动从数据库连接池中获取 connection，并开启事务然后绑定到 ThreadLocal 上，对于@Transactional注解包裹的整个方法都是使用同一个connection连接。如果我们出现了耗时的操作，<font style="color:#E8323C;">比如第三方接口调用，业务逻辑复杂，大批量数据处理等就会导致我们我们占用这个connection的时间会很长，数据库连接一直被占用不释放</font>。一旦类似操作过多，就会导致数据库连接池耗尽；

在一个事务中执行RPC操作导致数据库连接池撑爆属于是典型的长事务问题，类似的操作还有在事务中进行大量数据查询，业务规则处理等。

**长事务的危害:**

 1,数据库连接池被占满，应用无法获取连接资源；

 <font style="color:rgb(53, 53, 53);">2,容易引发数据库死锁；</font>

 3,<font style="color:rgb(53, 53, 53);">在主从架构中会导致主从延时变大;</font>

<font style="color:rgb(53, 53, 53);"> 4,</font>数据库回滚时间长.

**解决:**

<font style="color:#E8323C;">解决长事务的宗旨就是 对事务方法进行拆分，尽量让事务变小，变快，减小事务的颗粒度。</font>

<font style="color:#E8323C;"></font>

## 2 长事务
### 2.1）Spring实现事务
#### 声明式事务
 通过在方法上使用@Transactional注解进行事务管理的操作叫声明式事务；

 **优点,**很明显，就是使用很简单，可以自动帮我们进行事务的开启、提交以及回滚等操作。使用这种方 式，程序员只需要关注业务逻辑就可以了；


 ** 缺点,**就是事务的颗粒度是整个方法，无法进行精细化控制.

#### 编程式事务:
** **基于底层的API，开发者在代码中手动的管理事务的开启、提交、回滚等操作，spring项中可以使用

 TransactionTemplate类的对象，手动控制事务;

**代码事例子**

```plain
@Autowired
private TransactionTemplate transactionTemplate;

...


public void save(RequestBill requestBill) {

 transactionTemplate.execute(transactionStatus -> {
 requestBillDao.save(requestBill);
 //保存明细表
 requestDetailDao.save(requestBill.getDetail());
 return Boolean.TRUE;
 });
}
```

### 2.3）解决长事务
#### <font style="color:rgb(89, 89, 89);"> a.</font>将查询(select)方法放到事务外
在使用<font style="color:rgb(89, 89, 89);">@Transactional注解开启事务的时 ,可以将queryData1和queryData2两个查询方法放在事务外执行，不过 addData1(),updateData2() </font> 这两个方法需要放到另外一个类的事务方法里。

```plain
@Transactional(rollbackFor=Exception.class)
 public void save(User user) {
 queryData1();
 queryData2();
 addData1();
 updateData2();
 }
```

#### b.使用TransactionTemplate的编程式事务
```plain
 @Autowired
 private TransactionTemplate transactionTemplate;

 ...

 public void save(final User user) {
 queryData1();
 queryData2();
 transactionTemplate.execute((status) => {
 addData1();
 updateData2();
 return Boolean.TRUE;
 })
 }
```

#### c.避免远程调用
<font style="color:rgb(89, 89, 89);">我们在接口中调用其他系统的接口是不能避免的，由于网络不稳定，这种远程调的响应时间可能比较长，如果远程调用的代码放在某个事物中，这个事物就可能是大事务。当然，远程调用不仅仅是指调用接口，还有包括：发MQ消息，或者连接redis、mongodb保存数据等。</font>

<font style="color:#F5222D;">反例：使用@Transactional事务方法中有远程调用</font>

```plain
@Transactional(rollbackFor=Exception.class)
 public void save(User user) {
 #远程调用
 callRemoteApi();
 addData1();
 }
```

<font style="color:#F5222D;">正例：</font>

<font style="color:rgb(89, 89, 89);">远程调用的代码可能耗时较长，使用</font>TransactionTemplate的编程式事务，将远程调用放在事务外

```plain
 @Autowired
 private TransactionTemplate transactionTemplate;

 ...

 public void save(final User user) {
 #远程调用（http、redis、mq、rpc等）
 callRemoteApi();

 #执行本地的事务
 transactionTemplate.execute((status) => {
 addData1();
 return Boolean.TRUE;
 })
 }
```

<font style="color:#F5222D;">远程调用放在事务外如何保证事务一致性：</font>

远程调用的代码不放在事务中如何保证数据一致性呢？这就需要建立：重试+补偿机制，达到数据最终一致性了 。


#### d.事务中避免一次处理太多数据
<font style="color:rgb(89, 89, 89);">如果一个事务中需要处理的数据太多，也会造成大事务问题。比如为了操作方便，你可能会一次批量更新1000条数据，这样会导致大量数据锁等待，特别在高并发的系统中问题尤为明显。</font>

<font style="color:rgb(89, 89, 89);">解决办法是分页处理，1000条数据，分50页，一次只处理20条数据，这样可以大大减少大事务的出现。</font>

<font style="color:#F5222D;">一次处理太多数据也会造成长事务？</font>

<font style="color:rgb(89, 89, 89);"></font>

#### <font style="color:rgb(89, 89, 89);">e.</font>非事务执行
<font style="color:rgb(89, 89, 89);">在使用事务之前，我们都应该思考一下，是不是所有的数据库操作都需要在事务中执行？</font>

```plain
 @Autowired
 private TransactionTemplate transactionTemplate;

 ...

 public void save(final User user) {
 transactionTemplate.execute((status) => {
 addData();
 addLog();
 updateCount();
 return Boolean.TRUE;
 })
 }
```

addLog增加操作日志方法 和 updateCount更新统计数量方法,是可以不在事务中执行的，因为操作日志和统计数量这种业务允许少量数据不一致的情况；

当然大事务中要鉴别出哪些方法可以非事务执行，其实没那么容易，需要对整个业务梳理一遍，才能找出最合理的答案。


#### f.异步处理
我们需要考虑的是事务中的不一定所有的方法都需要同步执行？我们都知道，方法同步执行需要等待方法返回，如果一个事务中同步执行的方法太多了，势必会造成等待时间过长，出现大事务问题。

```plain
 @Autowired
 private TransactionTemplate transactionTemplate;

 ...

 public void save(final User user) {
 transactionTemplate.execute((status) => {
 order();
 delivery();
 return Boolean.TRUE;
 })
 }
```

order方法用于下单，delivery方法用于发货，下单之后不一定要马上发货，因此发货功能可以采用mq处理。

```plain
 @Autowired
 private TransactionTemplate transactionTemplate;

 ...

 public void save(final User user) {
 #下单在事务方法里
 transactionTemplate.execute((status) => {
 order();
 return Boolean.TRUE;
 })

 #发货采用异步mq的形式
 sendMq();
 }
```
