**<font style="color:rgb(8,15,23);">先广后深，打造自己的核心竞争力。 </font>**<font style="color:rgb(8,15,23);">你可以是微服务领域的专家，也可以是 ES 大佬，或者精通 Flink。 </font>

<font style="color:rgb(8,15,23);">一线城市工作的，技术迭代更新比较快，一定要跟紧主流技术。 </font>

## 🧭 架构师成长路线图（适合应届生）
我把它分成了 **四个阶段 + 对应目标与练习建议**
---

### ✅ 阶段 1：从“写功能”到“设计系统”（适合当前阶段）
#### 目标
+ 理解完整系统架构
+ 能自己搭建一个中小型项目的后端架构

#### 推荐内容
| 技能方向 | 具体内容 |
| --- | --- |
| 架构视角 | 单体 vs 微服务，分层架构，接口设计原则（RESTful） |
| 常用组件 | Redis、MQ（RabbitMQ/Kafka）、MySQL、Nginx |
| 技术基础 | Spring Boot + MyBatis + Redis + MQ 的整合开发 |
| 工程能力 | Git + Maven + Swagger + Nacos 注册中心 |
| 项目实践 | 设计并实现一个中等复杂系统（如订单系统、博客平台、IM聊天服务） |


#### 练习建议
+ 自己设计并开发一个「具有注册登录、权限、消息、缓存、异步任务」的系统
+ 每一个模块都写一份小型“架构说明”：这个功能为什么这样拆？选了哪些技术？为什么这样设计数据结构？

---

### ✅ 阶段 2：系统设计入门（开始做架构思考）
#### 目标
+ 掌握常见系统设计套路
+ 能在面试中应对“如何设计一个XXX系统”的问题

#### 学习重点
| 主题 | 重点内容 |
| --- | --- |
| 架构套路 | 如何做限流、缓存穿透、幂等设计、服务解耦 |
| 分布式 | 分布式ID、CAP、事务方案（本地消息表、TCC） |
| 数据库设计 | 表结构设计规范、索引、分库分表 |
| 框架源码 | ThreadPoolExecutor、ConcurrentHashMap、AOP、Spring Bean生命周期等源码 |
| 日志监控 | ELK、Prometheus 简单了解即可 |


#### 实战题目推荐
1. 如何设计一个“秒杀系统”？
2. 设计一个“短链接服务”
3. 设计一个“高并发下的评论系统”
4. 电商订单系统如何保证“高可用 + 幂等 + 唯一性 + 超卖控制”？

我可以陪你做这些题，每道题我们都可以拆成多个维度打分（功能性设计、系统拆分、技术选型、可扩展性、性能考虑等）

---

### ✅ 阶段 3：从代码工程师到业务工程师（技术+业务）
#### 目标
+ 懂业务、能用技术驱动业务优化
+ 能给团队输出技术解决方案、技术中台

#### 推荐你开始研究
+ 业务建模（领域驱动设计）
+ 服务中台（用户中心、权限中心、商品中心如何抽象复用）
+ 系统演进思维（从单体到微服务，哪些模块先拆，拆了后怎么治理）

可以找一个你写过的项目，尝试把它“领域建模 + 中台化”

---

### ✅ 阶段 4：工程体系与团队协作（成为带人的人）
这阶段可以在 1-2 年后再深入（如 CICD、测试体系、代码规范体系、架构评审流程等）

## 🧩 一、Jenkins 不是“平台”，只是“工具”
Jenkins、GitHub Actions、GitLab CI 本质上只是**CI/CD 的执行器或编排器**，特点是
+ 构建能力强，但 **体验原始**
+ 脚本驱动（如 `Jenkinsfile`），**门槛对业务开发偏高**
+ 分布式部署、权限控制、参数化、发布记录等都需要“拼凑”

换句话说
Jenkins 是 CI/CD 的“发动机”，但不是“汽车”

---

## 🏗️ 二、那“CI/CD 平台”到底干什么的？
它们是为了让“使用 CI/CD”变得更简单、更智能、更系统化。

### 常见功能模块如下
| 模块 | 功能描述 |
| --- | --- |
| 应用管理 | 统一注册所有项目（多语言支持） |
| 流水线模板 | 提供可视化配置的部署流程（支持 Maven/Node.js/Docker 等） |
| 一键发布 | 可以点击“发布到测试环境 / 灰度环境 / 生产环境” |
| 回滚机制 | 记录每一次发布，失败自动回滚 |
| 权限管理 | 不同项目、不同环境有不同权限 |
| 集群支持 | 对接 Kubernetes、Docker Swarm、多机部署 |
| 自动通知 | 钉钉、邮件、飞书等通知部署状态 |
| 多环境配置 | dev / test / staging / prod 环境自动切换参数、变量 |
| 可观测性 | 对接 Prometheus、ELK，部署后自动监控服务状态 |


📝 举个例子：腾讯的蓝盾（BlueKing）、阿里云的流水线、字节跳动的 CI 平台，都是自己造的。

---

## 🧠 三、为什么要“造平台”？
1. **规模化场景下，Jenkins 脚本不可控**
 - 每个项目都写一份 `Jenkinsfile`，维护困难、标准不统一
2. **对业务团队门槛高**
 - 普通开发不会写构建脚本，想上线还得找运维或架构师
3. **权限、审计、发布记录很重要**
 - 某次发布谁点的？哪个版本上线了？有操作记录吗？
4. **需要自定义流程、插件化、模板化**
 - 有的业务要求发布必须经过安全扫描 + 灰度验证 + 审批流程
5. **支持多语言 / 多架构**
 - Java、Node.js、Go、Python 同时支持 + 不同项目部署到不同集群

所以
自研 CI/CD 平台 ≈ 把 Jenkins（等工具）打包成“一个可视化、标准化、低门槛、团队可控”的平台

## 🔚 总结一句话
你看到的“CI/CD 平台项目”，其实是
对 CI/CD 工具链的一次“平台化封装”，**让整个交付流程标准化、可控、可视化、低门槛**

这正是中大型公司工程效能提升的关键路径，也正是很多优秀工程师晋升架构师所做的“技术中台”方向。


## 1️⃣ 这种 CI/CD 平台算“业务类项目”吗？
**答：不是传统意义上的业务项目，但它是“企业级技术中台”中的一种，属于工程效率工具类平台。**

+ ❌ 它不像电商、支付系统那样直接面对终端用户
+ ✅ 它服务的是内部工程团队（开发、测试、运维、架构师）
+ ✅ 它属于 **工程平台/DevOps平台/CI平台/发布平台** 范畴，是大型公司非常重视的一类基础设施

可以理解为
CI/CD 平台 = “为开发者写的业务系统”，目标是提升整个公司的交付效率和研发质量

所以你可以说它是**To Developer 的“业务系统”**（不像商城是 To C 的）

---

## 2️⃣ 这种平台一般用什么语言写？Java 吗？
**答：Java 是主流语言之一，但不是唯一。**

### 主流语言选择
| 语言 | 适用情况 | 说明 |
| --- | --- | --- |
| **Java** | 企业团队，后台逻辑复杂、权限多、流程长 | Spring Boot + MyBatis 最常见 |
| **Go** | 性能要求高，部署灵活，轻量服务 | CI 执行器、镜像构建服务常用 |
| **Node.js** | 配套前后端统一开发 / 前端主导场景 | 前后端都用 JavaScript，开发快 |
| **Python** | 脚本自动化、运维团队偏好 | DevOps 方向常见 |


📌 比如字节跳动、腾讯、京东的内部平台，大多是
+ **后端用 Java 或 Go**
+ **前端用 Vue / React**
+ 有些构建任务（如 Docker 镜像生成、SSH 发布）用 Python 脚本完成

---

## 3️⃣ 这种平台并发量高吗？能作为高并发项目锻炼吗？
**答：看你在哪一层！**

### ① 正常情况下：**UI层访问量不大，主要是内部使用（并发较低）**
+ 平时提交构建/部署操作的人不多（通常就是开发和运维）
+ 所以“页面访问/操作”并发 ≈ 低（几十并发即可满足）

### ② 但是！！**构建执行层/部署调度层并发是可以很高的！**
比如
+ 有 1000 个项目，每天都在提交代码
+ 每天跑几百个流水线，每个流水线可能触发
 - Docker 构建（消耗 CPU）
 - 自动部署（占用 SSH / API）
 - 测试任务（消耗资源）
 - 发布集群（调度 K8s）

这时
**并发执行任务数 + 资源调度效率 + 服务隔离性** 变得非常关键

### 所以结论是
CI/CD 平台的 **“调度/执行/构建引擎”部分，可以作为高并发项目去设计和优化！**
