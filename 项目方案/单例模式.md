## 单例模式：全班只发一瓶可乐的故事
### 一、设想一下
你们全班上 Java 课，老师说：“来，今天奖励大家一瓶冰可乐。”

**所有人眼睛放光**，结果——老师只从包里掏出**一瓶**！

此时，全班共享**这唯一的一瓶可乐**，谁都不能多喝，不能重复拿，也不能自己偷偷带一瓶进来……

这就是单例模式（Singleton Pattern）！

---

## 二、单例的“官方说法”翻译
**定义**
单例模式保证**一个类只有一个实例**，并且提供一个**全局访问点**来获取它。

**通俗版**
系统里只允许你“new”一次，就像那瓶可乐，谁都别想多来一瓶！

---

## 三、为什么要这么做？
### 场景来了
+ 你写了一个**日志系统**，结果 100 个线程一起“new Log()”写日志，
日志文件直接爆炸！
+ 你创建了数据库连接池，每次访问都“new Pool()”，
数据库表示：**我撑不住了兄弟……**

解决办法就是：**只造一个！全系统共用！**

+ **配置中心（ConfigManager）****：系统一启动，就从配置文件或远程服务器读取配置。**
+ **数据库连接池（DBPool）：系统只需要维护一个统一的数据库连接池，谁都不能自己偷偷 new 一个。**

## ** 四、Java 代码：**
## ** 1. 懒汉式（Lazy）——拖延症晚期选手 **
> 你喊我了，我才懒洋洋起床。
>

**适合**：资源初始化较重，启动时不一定用得上。

```java
public class ConfigManagerLazy {
 private static volatile ConfigManagerLazy instance;

 private ConfigManagerLazy() {
 System.out.println("从服务器加载配置...");
 }

 public static ConfigManagerLazy getInstance() {
 if (instance == null) {
 synchronized (ConfigManagerLazy.class) {
 if (instance == null) {
 instance = new ConfigManagerLazy();
 }
 }
 }
 return instance;
 }

 public String getConfig(String key) {
 return "读取配置: " + key;
 }
}
```

 调用示例
```java
public class Main {
 public static void main(String[] args) {
 ConfigManagerLazy config = ConfigManagerLazy.getInstance();
 System.out.println(config.getConfig("server.port"));
 }
}
```

### 2. 饿汉式（Eager）——卷王型选手
> 系统一启动，哥就准备好了！
>

**适合**：实例轻量，不占资源，一定会用。

```java
public class DBPoolEager {
 private static final DBPoolEager instance = new DBPoolEager();

 private DBPoolEager() {
 System.out.println("连接池初始化：连接若干数据库...");
 }

 public static DBPoolEager getInstance() {
 return instance;
 }

 public void getConnection() {
 System.out.println("获取数据库连接");
 }
}

```

 调用示例
```java
public class Main {
 public static void main(String[] args) {
 DBPoolEager pool = DBPoolEager.getInstance();
 pool.getConnection();
 }
}
```

## 两者区别大对决
| 特点 | 懒汉式 | 饿汉式 |
| --- | --- | --- |
| 是否延迟加载 | 是 | 否 |
| 是否线程安全 | 是（需加锁或双重检查） | 是（类加载时初始化） |
| 启动性能 | 快 | 慢（因为提前初始化） |
| 占内存 | 有可能低 | 稍高 |
| 实例控制 | 稍复杂 | 简单明了 |


## 推荐实践策略
| 场景 | 推荐写法 |
| --- | --- |
| 高性能/轻量组件 | 饿汉式 |
| 重型资源（远程调用/文件读） | 懒汉式 |
| 希望极致安全与简洁 | 枚举单例 |

## 单例模式的 **全家桶写法汇总**
### 1. **懒汉式（线程不安全）— 不推荐**
```java
public class Singleton {
 private static Singleton instance;

 private Singleton() {}

 public static Singleton getInstance() {
 if (instance == null) {
 instance = new Singleton(); // 多线程下可能创建多个实例
 }
 return instance;
 }
}
```

> **问题**：线程不安全，容易“多生娃”。
>

---

### 2. **懒汉式（线程安全 + 同步方法）**
```java
public class Singleton {
 private static Singleton instance;

 private Singleton() {}

 public static synchronized Singleton getInstance() {
 if (instance == null) {
 instance = new Singleton();
 }
 return instance;
 }
}
```

> **问题**：线程安全了，但性能太差，谁都得排队。
>

---

### 3. **懒汉式（双重检查锁 DCL）— 推荐使用**
```java
public class Singleton {
 private static volatile Singleton instance;

 private Singleton() {}

 public static Singleton getInstance() {
 if (instance == null) {
 synchronized (Singleton.class) {
 if (instance == null) {
 instance = new Singleton();
 }
 }
 }
 return instance;
 }
}
```

> **优点**：懒加载 + 线程安全 + 性能好，一般实战用这个。
>

---

### 4. **饿汉式（类加载即创建）**
```java
public class Singleton {
 private static final Singleton instance = new Singleton();

 private Singleton() {}

 public static Singleton getInstance() {
 return instance;
 }
}
```

> **适合**：实例创建开销小且必用。
>

---

### 5. **静态内部类实现 — 延迟加载 + 线程安全**
```java
public class Singleton {
 private Singleton() {}

 private static class Holder {
 private static final Singleton INSTANCE = new Singleton();
 }

 public static Singleton getInstance() {
 return Holder.INSTANCE;
 }
}
```

> **优雅！** 利用类加载机制实现懒加载和线程安全。性能好，代码清晰，推荐！
>

---

### 6. **枚举实现（最安全）— Java 官方推荐！**
```java
public enum Singleton {
 INSTANCE;

 public void doSomething() {
 System.out.println("我是唯一的枚举单例！");
 }
}
```

> **优点**：天生线程安全、防反射、防反序列化破坏、代码超简单！
>

## 一、Spring 中的单例模式：用得最凶的框架
### Spring 中的 Bean 默认就是 **单例模式**！
```java
@Component
public class HelloService {
 public void sayHello() {
 System.out.println("Hello from Singleton Bean!");
 }
}
```

```java
@RestController
public class HelloController {

 @Autowired
 private HelloService helloService;

 @GetMapping("/hi")
 public String hi() {
 helloService.sayHello();
 return "Hi!";
 }
}
```

### Spring 是怎么做的？
+ Spring 容器启动时，扫描所有 `@Component`、`@Service`…
+ 默认构建并缓存成单例（放在 BeanFactory 缓存里）
+ 你每次 `@Autowired` 拿到的，都是 **同一个实例**

所以：你根本不用手写单例，Spring 已经帮你搞定了！

### 想改成多例怎么办？
```java
@Scope("prototype")
@Component
public class NotSingleton {
 // 每次注入都会新建
}
```

## 二、Spring 中的单例实践：配置中心
```java
@Component
public class AppConfig {
 private final Map<String, String> config = new HashMap<>();

 @PostConstruct
 public void load() {
 // 假装读取文件或远程配置
 config.put("env", "dev");
 config.put("timeout", "3000");
 }

 public String get(String key) {
 return config.get(key);
 }
}
```

**调用：**

```java
@Autowired

String env = appConfig.get("env");
```

Spring 只创建一个 `AppConfig`，你在哪用都是“同一瓶可乐”。

## 三、MyBatis 中的单例：SqlSessionFactory
```java
public class MyBatisUtil {
 private static SqlSessionFactory sqlSessionFactory;

 static {
 try (InputStream inputStream = Resources.getResourceAsStream("mybatis-config.xml")) {
 sqlSessionFactory = new SqlSessionFactoryBuilder().build(inputStream);
 } catch (IOException e) {
 throw new RuntimeException(e);
 }
 }

 public static SqlSession openSession() {
 return sqlSessionFactory.openSession();
 }
}
```

### 注意！
+ `SqlSessionFactory` 是线程安全的，推荐做成**单例**
+ `SqlSession` 是线程不安全的，每次都要新建，用完关掉！

## 四、Spring + MyBatis 整合中的单例

```xml
</bean>
```

这也是单例！Spring 容器只会创建一次 SqlSessionFactory，并重复使用。

**单例模式**（Singleton Pattern）是一种常见的设计模式，确保一个类在整个应用程序中只有一个实例，并提供全局访问该实例的方式。

### 一、单例模式的作用
1. **确保全局唯一实例**：通过控制实例的生成，保证系统中该类只有一个实例存在，避免重复实例化带来的资源浪费或逻辑错误。
2. **全局访问点**：为某些需要全局唯一访问的资源或服务（如配置管理器、日志记录器、数据库连接池等）提供统一访问点。

### 二、为什么要使用单例模式？
1. **节省资源**：在某些情况下，频繁创建对象会浪费大量内存或计算资源，使用单例可以节省这些资源，避免不必要的性能开销。例如，数据库连接、线程池、日志管理器等资源通常是重型的，频繁创建和销毁可能影响系统性能。
2. **控制资源共享**：确保某些资源（如打印机、文件等）的唯一性，防止多个实例之间的竞争和不一致行为。例如，多个线程访问一个共享资源时，单例模式可以防止并发问题。
3. **简化系统管理**：某些资源或服务在应用程序运行期间需要始终保持一致状态。使用单例模式，能够确保系统的统一性和一致性。

### 三、单例模式的优势
1. **减少内存开销**：单例模式限制了对象的创建，保证只有一个实例存在，避免重复创建，减少内存开销。
2. **减少系统开销**：某些实例化过程可能比较耗费时间和资源（如加载大型配置文件或建立数据库连接），单例模式避免了重复初始化的开销。
3. **线程安全**：适当的单例实现可以避免多个线程并发创建多个实例的情况，保证了线程安全性。
4. **提供全局访问**：由于单例对象可以通过全局访问点获得，因此它能简化系统设计，方便管理一些全局状态或资源。

### 四、单例模式的劣势
1. **隐藏类的依赖性**：单例的全局访问点会使系统变得隐式依赖它，不容易测试或调试。
2. **不利于扩展**：由于单例类不能被实例化多个对象，这种限制有时可能阻碍了程序的扩展性。
3. **生命周期难以控制**：由于单例对象存在整个程序生命周期中，内存释放时机往往不可控，可能会导致内存泄漏等问题。

### 五、单例池（Singleton Pool）
**单例池**可以理解为一种扩展的单例模式。它结合了对象池（Object Pool）的概念，能够根据需求生成多个有限的实例，而不是严格只生成一个。单例池的应用场景类似于线程池或数据库连接池。

+ **用途**：当单例模式不适合于多个对象需求时，但又希望限制创建的对象数量时，可以使用单例池。它限制了特定资源的实例数量，避免频繁创建和销毁资源。
+ **好处**：可以在提高性能的同时保留一定的灵活性。例如，在某些应用场景下，一个实例不够用，但同时又不想让系统无限制地创建实例，此时可以用单例池来限制对象的数量。

### 六、总结
1. **单例模式**适合用于系统中的某些全局资源，如日志管理器、数据库连接、配置文件管理器等。
2. **单例模式的好处**在于节省资源、保证资源一致性、全局访问方便，但在大型系统中可能隐藏依赖关系，不利于扩展。
3. **单例池**是一种限制多个实例的模式，介于单例和对象池之间，适合用于控制对象实例数量但又不完全限制为一个的场景。

这两者在不同场景下各有用武之地，可以根据应用场景的具体需求灵活选择。


在依赖注入框架（如Spring、Dagger等）中，`@Scope`注解用于定义对象的**生命周期**，决定一个对象在不同上下文中是如何创建和管理的。对于**单例模式**的使用，取决于对象的用途、生命周期管理以及共享的必要性。

### 一、Scope注解
`@Scope`是用于控制对象的**作用域**，其生命周期通常决定于框架的容器或上下文环境。常见的作用域有
1. **Singleton（单例）**：在整个应用程序的生命周期内，某个类只有一个实例。常用于那些需要全局共享的资源或服务。
2. **Prototype（原型）**：每次注入时，都会创建一个新的实例。通常用于需要隔离状态的对象，不共享实例。
3. **Request（请求作用域）**：在Web应用程序中，每次HTTP请求创建一个新实例，且只在该请求的生命周期内存在。
4. **Session（会话作用域）**：每个用户的Session期间创建一个实例，同一会话中共享该实例。

### 二、为什么有些对象需要单例模式？
#### 1. **全局唯一性需求**
一些类的实例在整个应用程序中需要保持全局唯一性，因此适合使用**单例模式**，例如
+ **配置类**：如应用程序的配置管理器，整个应用程序需要共享同一个配置状态，配置的变更应在整个系统中即时生效。
+ **数据库连接池**：数据库连接是一种重型资源，频繁创建和销毁会带来性能消耗，因此需要通过单例模式来管理，确保在整个应用中共享一个连接池。
+ **缓存服务**：缓存是系统全局的状态，需要不同模块、服务之间共享，因此使用单例模式确保全局唯一。
+ **日志管理器**：在应用程序的各个模块都可能需要记录日志，因此日志系统通常是单例的，便于各模块使用统一的日志管理工具。

#### 2. **节省资源**
某些类在实例化时代价高昂，如初始化需要加载大量数据或依赖外部资源（如网络、文件等），为了避免频繁创建和销毁，可以使用**单例模式**。例如
+ **外部API服务的客户端**：需要频繁调用外部API，但每次调用都创建一个客户端对象会浪费大量的时间和资源，因此可以通过单例模式来复用这个客户端对象。

#### 3. **共享状态**
有些服务或对象需要在多个组件之间共享状态或数据，单例模式可以帮助实现这个功能。例如
+ **Session管理**：在Web应用程序中，Session通常由单例管理，因为它需要在多个请求中共享用户的状态信息。

#### 4. **全局一致性**
对于某些类，全局共享一个实例可以确保一致的行为或状态。例如
+ **系统配置类**：如果不同的部分使用了不同的实例，可能导致系统配置不一致，影响系统行为。

### 三、为什么有些对象不需要单例模式？
#### 1. **状态隔离**
有些类实例需要各自独立的状态，如果使用单例，可能会引发状态冲突，甚至造成意料之外的错误。例如
+ **原型模式对象**：比如，表单对象、用户输入对象，每个请求可能会包含不同的状态和数据。如果使用单例，不同用户之间可能会共享状态，导致数据不一致和安全问题。因此在这种场景下，每次请求需要创建一个新的实例。

#### 2. **线程安全问题**
如果多个线程访问同一个单例对象并修改其内部状态，可能会产生并发问题。因此，某些类不适合使用单例，除非该类是**无状态的**或已经设计为线程安全。

#### 3. **生命周期不同**
某些对象只需要在特定的上下文中存在，比如只在**某个请求**或**某个会话**中存在，并不需要全局共享。例如
+ **Request作用域的对象**：适用于Web应用中的每个HTTP请求。如果使用单例模式，这些对象在多个请求之间共享，会导致状态不一致或错误。
+ **Session作用域的对象**：每个用户的会话期间需要独立的对象实例，如果采用单例模式，会导致不同用户之间共享数据，从而导致数据泄漏。

### 四、单例模式的优势和Scope的关系
+ **单例模式的优势**在于节省资源和保持全局一致性，但需要确保全局共享不会引发状态冲突或线程安全问题。因此，单例对象适用于那些**无状态**或**状态全局一致**的类。
+ **Scope控制的对象生命周期**则允许根据不同场景创建不同的对象实例，避免全局状态冲突的问题。例如，对于某些**有状态的类**或**隔离要求高的对象**，可以使用`@Prototype`、`@RequestScope`等作用域注解，确保对象实例的隔离性和独立性。

### 五、单例池的使用场景
+ 当系统既需要节省资源又需要一定的隔离时，可以采用**单例池**，通过创建**有限数量的实例**来满足不同请求的并发需求，而不是严格限制只有一个实例。例如，在高并发场景下的数据库连接池、线程池等。

### 六、总结
+ **使用单例模式**的对象通常是全局唯一的，能够共享的资源，如数据库连接、日志管理器等。
+ **不使用单例模式**的对象通常是有状态的，且需要在不同上下文中隔离，避免状态冲突。
+ **Scope注解**提供了灵活的对象生命周期管理，可以在需要时使用单例模式，而在其他场景下使用更合适的作用域，如原型、请求或会话作用域。

选择是否使用单例模式，取决于对象的**状态管理需求**、**生命周期要求**以及**资源共享的必要性**。
