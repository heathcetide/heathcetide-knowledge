## 1. 同步（Synchronous） VS 异步（Asynchronous）
| | 同步 | 异步 |
| --- | --- | --- |
| 发出请求后 | **等结果回来**才能继续做事 | **不用等结果**，可以继续做其他事情 |
| 例子 | 打电话订餐，等送到才能走 | 打电话订餐，挂了继续玩，送到了再通知 |
| 程序中体现 | 发请求后，程序暂停，等结果 | 发请求后，继续跑，结果回来时另处理 |
| 适合场景 | 很快能返回，等一下没关系 | 返回慢，或者需要同时干很多事 |


---

## 2. 阻塞（Blocking） VS 非阻塞（Non-Blocking）
| | 阻塞 | 非阻塞 |
| --- | --- | --- |
| 程序执行时 | 卡住等待资源就绪 | 如果资源没好，**立刻返回**或继续尝试 |
| 例子 | 打电话给客服，一直占线，你只能拿着电话傻等 | 打电话占线，系统告诉你排队中，你去干别的 |
| 程序中体现 | 调用一个方法，线程直接停在那 | 调用后，不用卡住线程，可以继续 |
| 适合场景 | 小规模操作，短时间等待 | 高并发场景，不想浪费CPU时间 |


---

# 一个总结口诀
记住下面这一句，你就不会搞混
**同步异步：看有没有"等结果"；阻塞非阻塞：看有没有"卡线程"。**

+ **同步异步 →** 是**思维方式**问题：要不要等结果？
+ **阻塞非阻塞 →** 是**执行状态**问题：线程有没有卡死？

# 四种组合全图
| 组合 | 含义 |
| --- | --- |
| 同步 + 阻塞 | 常规调用，发出后傻等，线程卡住（最常见，最浪费） |
| 同步 + 非阻塞 | 发出后，如果没完成马上返回，之后自己查询（轮询） |
| 异步 + 阻塞 | 很少，异步发出，但通知回来时卡住线程处理 |
| 异步 + 非阻塞 | 最理想！发出后继续做事，结果回来时回调处理 |


---

# 超通俗的生活比喻
想象你去医院挂号
| 方式 | 说明 |
| --- | --- |
| 同步+阻塞 | 挂号排队，只能傻等，不干别的。 |
| 同步+非阻塞 | 挂号排队，但窗口告诉你还有20分钟，你每5分钟回来问一下。 |
| 异步+阻塞 | 你委托护士帮你排队，但护士在帮你时自己卡住了（不干其他事）。 |
| 异步+非阻塞 | 你挂了号，护士帮你排着，你自己逛医院，叫到号了护士通知你。 |


最舒服的是**异步+非阻塞**，最高效，最合理！

# 程序中具体怎么写？
+ **同步阻塞**（传统调用）
```plain
String result = httpClient.get("https://example.com");
// 调用后必须等到result返回，卡住线程
```

+ **异步非阻塞**（用异步+回调）
```plain
httpClient.getAsync("https://example.com", response -> {
 System.out.println("收到返回了: " + response);
});
// 调用后马上继续干别的
```

---

# 总结一句话
**同步异步是"要不要等结果"的问题，阻塞非阻塞是"线程要不要卡死"的问题。**
想要高并发、高性能，就得用**异步+非阻塞**的设计！
